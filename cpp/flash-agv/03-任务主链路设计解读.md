# flash-agv 任务主链路设计解读

> 本文按当前源码解释系统如何组织，不等于个人贡献清单。个人范围参见 `hehongjie开发文件与函数范围.md`；当前源码中的后续改动与历史初版需区分。本轮只做静态阅读，未运行车端程序。

## 从系统到模块

```text
RCS VDA5050 OrderMessage
  → CommAdapterManager：通信回调
  → TaskManager：任务生命周期与编排
      → MapManager：把订单点/边关联地图属性
      → NavStitcher：续单路径拼接、起点索引、移动类型
      → NavPruner：按当前位置及约束计算可下发区间
      → NavBaseClient → NavBase：目标下发、反馈与结果
  → StateManager：保存任务状态和错误
  → CommAdapterManager：上传 VDA5050 StateMessage
```

`TaskManager` 是调度与导航之间的编排层。它不实现 VDA5050 的底层收发，也不实现轨迹规划或底盘控制。`src/order_manager/CMakeLists.txt` 将它与拼接、裁断、导航客户端组成 `order_manager` 静态库，再由 `flash_agv` 程序链接。

## 一单任务的状态变化

1. **收到订单**：`CommAdapterManager::activateBusinessHandlers` 注册订单回调，调用 `TaskManager::taskInit`。`taskTransform` 校验节点与边的数量关系，把协议节点、边转为 `TaskPath`，借助 `MapManager` 补齐地图属性。当前代码遇到首节点 `released=false` 会先返回，不进入后续执行。
2. **接续路径**：`taskInit` 取出原路径，交给 `NavStitcher::stitchOrders`。首单直接建立路径；续单寻找旧路径后缀与新路径前缀的重叠段，再追加新点。`calcStartIndex` 在首单中先检查车是否位于某点，未命中则把车位姿投影到候选路段，选择起始索引。
3. **启动执行**：首单依次进入任务 FSM 的 `WAITING`、`INITIALIZING`；`taskProcess` 在独立线程中以 10 Hz 调用 `executeTask`，续单沿用正在运行的生命周期。
4. **确定当前路径位置**：`executeTask` 读取位姿、导航反馈和结果；`preprocessing` 对齐目标与反馈的 `task_code`，`getRouteLoc` 结合反馈索引、上次下发目标和当前位姿确定路线位置。
5. **下发导航段**：`NavPruner::pruneOrders` 对候选区间应用顺滑过点、行驶类型、上道、放行状态、轨迹等策略；前边界取各策略的最大值，后边界取最小值，得到 `[front, back)`。`preprocessGoal` 截取该段，`fillGoal` 转为 `NavBaseGoal`，`sendGoal` 通过 `NavBaseClient` 送给 `NavBase`。
6. **持续回报并收口**：运行中 `publishTaskStatus` 把任务状态写进 `StateManager`；状态快照经通信层上传。导航目标完成后，`fillResult` 判断结果是否属于当前目标且是否为最终目标；`taskProcess` 更新 FSM，发布成功或失败并清理任务。取消路径则调用 `cancelTask` 撤销导航目标并重置任务。

## 值得深入理解的设计

### 1. 滚动订单与正在执行的目标分开管理

调度可能先给 `A → B → C`，车在走向 `C` 时又给 `B → C → D`。拼接器保留旧路径并追加 `D`；当前正在执行的 `C` 目标可以继续，但它不再代表整单终点。当前 `taskInit` 对路径延长时的 `active_nav_goal_.is_final` 做了这种调整。这是“续单不打断当前导航”和“到 C 不误报整单完成”的组合问题。

### 2. 起点匹配与裁断是两次不同决策

`NavStitcher::calcStartIndex` 解决“这份路径从哪开始接车当前位姿”；`NavPruner::pruneOrders` 解决“这一轮实际允许下发到哪”。后者以路径索引区间为统一结果，把不同业务约束合并，而不是让任务主循环为每种场景另写一条下发流程。

### 3. 用任务标识处理迟到反馈

导航结果和调度续单异步到达。`task_code` 把下发目标与反馈、结果关联起来，`preprocessing` 对齐反馈，当前 `fillResult` 忽略不属于活动目标的迟到结果，并区分中间段完成与整单完成。对应的工程问题是防止旧反馈结算新任务、避免重复下发或过早结束。

### 4. 生命周期与错误出口集中

FSM 表达等待、初始化、运行、暂停、完成和失败；转换、拼接、位姿读取、目标组装及下发等错误由 `TaskManager` 上报。取消时撤销导航目标，执行完毕后重置路径、索引和状态。`StateManager` 负责对外状态事实，通信层负责协议上传。

## 与 nav-manager 的关系及个人范围

nav-manager 中相近职责分布在 `AccessLayer`、`NavPlugin`、`DispatchPreemptProcessor`、`Pruner` 和 `NavBaseClient`。flash-agv 将任务主链路组织为 `TaskManager`，把拼接和裁断分别放到 `NavStitcher`、`NavPruner`，入口改为 VDA5050 订单，状态出口改为 `StateManager`。两个版本的 `NavBaseClient` 都直接调用导航对象，不能把“首次改为进程内调用”作为成果。

开发范围清单将任务转换、初始化、路线位置计算、预处理、目标组装与下发、执行和取消等列为 hehongjie 参与的主链路，也将拼接器、裁断器列为较完整的开发范围。当前 `TaskManager` 里的取放货/充电行为树、异步业务动作以及部分活动目标结果保护属于后续扩展；讲个人项目时应按清单进一步核对具体边界。

## 源码入口

- `src/communication/comm_adapter_manager.cpp`：订单回调与状态上传。
- `src/order_manager/task_manager.cpp`：`taskTransform`、`taskInit`、`executeTask`、`taskProcess`、`fillResult`、`sendGoal`。
- `src/order_manager/stitcher.cpp`：路径拼接与起点匹配。
- `src/order_manager/pruner.cpp`：裁断策略与区间合并。
- `include/order_manager/common/nav_structs.h`：`TaskPath`、`RouteLocationInfo`、`PrunerIndex`、`InnerMBGoal` 等内部数据结构。
