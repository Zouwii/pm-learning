# Nav-Manager 任务决策学习与交接计划

## 一、目标

用三个月完成 `nav-manager` 中 `manager` 任务决策模块的 owner 交接：在团队既有导航框架上，吃透 hehongjie 主导建设和长期优化的核心决策链路，能够独立维护、开发业务需求、处理现场问题、完成版本发布，并主导至少一次可验证的可靠性升级。

这不是要把整个导航系统描述成个人从零开发，也不是改写历史提交归属。三个月后的合理目标是：成为任务决策模块的后续负责人，并对接管后的需求、设计、实现、验证和现场结果负责。

## 二、项目范围与边界

### 2.1 本计划的核心范围

```text
调度 / 行为树 / 单机任务
            ↓
AccessLayer：任务接收、校验、插件选择、抢占入口
            ↓
NavPlugin：任务初始化、决策编排、状态管理
            ↓
RouteProcessor / DispatchPreemptProcessor：任务标准化与路径处理
            ↓
Pruner：路径裁断与定位源边界处理
            ↓
HotStartManager / PrecisionManager / AbnormalCheck
定位决策、可行域与安全检查
            ↓
NavBaseClient：向执行层下发任务并接收结果
```

### 2.2 需要理解接口但不作为个人主线的范围

- `MapManager`：地图点、边、轨迹、定位源和热更新的数据契约；
- `NavBase`：任务执行、反馈、取消和异常返回；
- `NavController`、`LocalPlanner`：消费任务路径的方式及问题边界；
- `TagChecker`：具备现场维护能力，但只作为多定位源场景的辅助 Case。

### 2.3 不纳入个人成果的范围

- 团队长期建设的整个导航框架；
- 底层控制器、局部规划算法和多底盘运动学；
- hehongjie 或其他同事已经完成、而本人没有重新设计和交付的历史功能；
- 只阅读过代码但没有承担后续结果的模块。

## 四、必须吃下来的三条高价值链路

### 4.1 P0：任务生命周期与抢占决策

#### 目标

能解释和处理一条任务从接收到结束的完整生命周期，以及新旧任务、取消、抢占和异常同时发生时的状态一致性。

#### 重点模块

- `manager/src/access_layer.cpp`
- `manager/src/plugin/nav_plugin.cpp`
- `manager/src/utils/nav_base_client.cpp`
- `manager/src/dispatch/dispatch_preempt_processor.cpp`
- 对应头文件和共享状态结构

#### 必须掌握的问题

1. 不同任务入口如何完成校验、过滤和插件选择；
2. 首次任务、接续任务、抢占任务和重发任务如何区分；
3. Action goal、feedback、result、cancel 的时序关系；
4. Manager 与 NavBase 谁拥有哪一层状态；
5. 成功、失败、异常、取消后分别需要清理哪些状态；
6. 地图更新、反馈线程和任务回调之间有哪些共享状态；
7. 历史结果、重复回调或延迟返回为什么可能污染下一单任务；
8. 如何保证取消、抢占和状态重置可重复执行且不会互相覆盖。

#### 历史高价值问题类型

- 任务取消后状态没有完整复位；
- 新旧任务切换时残留旧结果；
- 抢占任务计数、反馈和实际执行状态不一致；
- MoveBase 完成状态更新时机错误；
- 单机任务与调度任务抢占语义不同；
- UUID 过滤和取消信号存在时序冲突；
- 行为树挂起任务与导航侧状态不一致；
- 异常状态没有正确向上传递或清理。

#### 完成标准

面对“上一单未结束、新任务进入、取消同时到达、底层延迟返回”等问题，能够独立画出时序、确定状态归属、定位根因、完成修复和回归，不再依赖原作者判断。

### 4.2 P0：路径处理、拼接与裁断决策

#### 目标

能够预测任意一条上游任务经过过滤、合并、起点计算、抢占处理和裁断后的实际下发结果，并解释每条业务规则存在的原因。

#### 重点模块

- `manager/src/router/route_processor.cpp`
- `manager/src/code_inserting/pruner.cpp`
- `manager/src/dispatch/dispatch_preempt_processor.cpp`
- `manager/src/router/route_generator.cpp`
- `NavPlugin` 中任务初始化和 `fillInnerMBGoal` 相关逻辑

#### 决策维度

| 维度 | 典型取值 |
| --- | --- |
| 任务来源 | 单机、新调度、老调度、第三方 |
| 任务关系 | 首次、接续、抢占、取消重发 |
| 点位关系 | 重复点、同 ID 不同角度、旋转点、过点 |
| 运动方式 | 前进、后退、横移、原地旋转、底盘与转盘组合 |
| 定位变化 | 激光、二维码、纹理切换 |
| 执行约束 | 路宽、footprint、可行域、终点精度 |

#### 必须掌握的问题

1. 起点索引如何计算，阈值来自哪里；
2. 多拍任务为什么需要合并，哪些情况禁止合并；
3. 重复点、重复 ID 和角度变化分别如何处理；
4. `move_type` 在合并和抢占后如何保持正确；
5. 上道、接续、跟车和单点任务有哪些特殊规则；
6. 硬裁断、顺滑裁断和定位源裁断分别解决什么问题；
7. `front`、`back`、`start_index` 和 `prune_index` 如何保证不越界；
8. 哪些任务段应该下发，哪些应该过滤或等待。

#### 完成标准

建立可执行的“任务类型 × 路径类型 × 定位源 × 抢占方式”测试矩阵；对历史典型路径进行回放时，能够在运行前写出预期下发结果，并与实际结果核对。

### 4.3 P1：定位决策、可行域与安全约束

#### 目标

巩固本人已有的多定位源 ownership，并掌握任务决策如何向安全模块传递路宽、footprint、可行域和货架状态。

#### 重点模块

- `manager/src/code_inserting/hotstart_manager.cpp`
- `manager/src/code_inserting/precision_manager.cpp`
- `manager/src/code_inserting/abnormal_check.cpp`
- `MapManager` 中与坐标转换、边属性和路宽有关的接口
- `NavPlugin` 中定位切换和安全约束下发逻辑

#### 必须掌握的问题

1. 当前边、下一条边和重复边如何共同决定定位源；
2. 定位源打开、等待有效、关闭旧定位源和失败降级的时序；
3. 激光、二维码等坐标系如何转换，怎样避免混用；
4. footprint、路宽、旋转方式和载货状态如何形成可行域；
5. 原地旋转为什么需要不同的安全边界；
6. 地图热更新如何影响正在执行的任务；
7. 安全数据错误时应拒绝任务、降级还是沿用默认值。

#### 完成标准

能够独立处理定位源切换失败、坐标系错误、路宽或 footprint 异常、货架角度和旋转可行域等现场问题，并能说明错误决策可能造成的安全影响。

## 五、整体架构学习的四项必备产出

### 5.1 系统边界图

标明调度、Manager、NavBase、Planner、Controller 的输入、输出、状态归属、错误返回和清理责任。

### 5.2 任务状态机

至少覆盖：

```text
Idle
  → Initializing
  → Executing
  → Preempting / Cancelling
  → Succeeded / Failed / Abnormal
  → Resetting
  → Idle
```

需要进一步标出当前代码分别用哪些变量表达这些状态、由哪些线程读写，以及哪些组合可能产生不一致。

### 5.3 路径决策矩阵

将分散在条件分支中的业务规则整理成可检索、可评审、可转化为测试的数据表，而不是只保留个人脑内理解。

### 5.4 线程与回调图

至少标明：

- Action execute 和 cancel 回调；
- AccessLayer feedback 线程；
- NavPlugin 高频、低频线程；
- 地图更新与定位源回调；
- MoveBase done、active、feedback 回调；
- 跨线程共享变量及其 mutex、atomic 或条件变量保护。
