# 到点自学习：Nav-Application + Nav-Manager

## 一句话

面向 AGV/AMR 多车到点一致性的自学习补偿产品：车端在真实任务结束后采集到点误差，服务端按“车—点—场景”聚合样本、估计误差分布中心并生成补偿，再通过地图数据下发到车端，在下一次任务中按场景匹配并安全应用。

## 我在这件事上的真实角色

我不是只做了一个导航接口，而是跨两个仓库承担了端到端开发：

| 仓库 | 系统角色 | 我的核心工作 |
| --- | --- | --- |
| `nav-application` | 服务端产品与操作入口 | 前后端、数据同步、补偿计算、结果下发、开关清理、自动化、精度分析与算法实验 |
| `nav-manager` | 车端导航执行闭环 | 场景数据采集、补偿解析与选择、目标位姿应用、有效性保护、状态重置及版本兼容 |

Git 证据显示：

- `nav-application` 自学习相关路径中，我在全分支留下约 317 个个人提交，关键 Go、Vue、计算和分析文件基本由我持续维护；
- `nav-manager` 的 `run_learning.cpp` 由我创建并长期主导迭代，同时在既有 `NavPlugin`、`MapManager` 和 `DataCollector` 框架中完成自学习接入；
- 这项工作从 2025 年 1 月持续迭代到 2026 年 7 月，覆盖功能建设、现场问题、产品化操作和算法实验。

> 提交数量只证明持续参与深度，不直接等于业务效果；全分支中存在合并和移植记录。

## 为什么要做

工业现场的到点误差并不是固定值，会受到机器人个体、目标点、前置点、末姿角、载荷、楼层、有码/无码方式及环境变化影响。

传统方式主要靠实施人员反复试跑和手工配置静态补偿，存在三个问题：

1. 多车到同一点位的一致性差；
2. 补偿容易随载荷、地面和设备状态变化而失效；
3. 标定、验证和维护成本高，经验难以沉淀。

产品目标不是重新做一个控制器，而是利用日常任务数据估计特定场景下的误差分布中心，自动形成可追踪、可下发、可关闭和可清理的补偿闭环。

## 端到端链路

```text
机器人完成真实导航任务
        ↓
Nav-Manager 采集到点样本
点位/前点/载荷/楼层/有码无码/补偿前后误差/当前补偿
        ↓
上传到 Ops，Nav-Application 同步并持久化
        ↓
按“车—点—场景 Key”分组，过滤无效样本
        ↓
估计误差分布中心，生成补偿和误差统计
        ↓
人工或自动流程审核、开关、清理
        ↓
通过 MapMaster 的 study_nodes 下发
        ↓
Nav-Manager 解析并在下一次任务初始化时匹配补偿
        ↓
修改实际导航目标，任务结束后继续采集
```

## 我做了什么开发

### Nav-Application：服务端产品主链路

1. 建设 Go + Vue + MySQL 的完整应用，而不是只写计算脚本。
2. 打通 Ops 原始数据同步、分块入库、场景字段预解析和 UUID 变更处理。
3. 设计并迭代 `raw_data`、`learning_result`、`learning_error` 及分发历史等数据结构。
4. 实现补偿计算、角度归一化、分组过滤和多种中心估计方法。
5. 打通补偿 JSON 生成、MapMaster 下发、地图同步和分发记录。
6. 提供全局/点位开关、清空全部、清空异常、置零、定时任务和锁保护。
7. 将“同步→计算→临时启用→下发→恢复开关”收敛成 `automate_action`。
8. 支持有码/无码、前置点、载荷、楼层和多现场版本差异。
9. 建设精度分析：按车辆和路径查看控制误差、定位误差、Tag 误差的均值、标准差和极值。
10. 将分析结果映射为继续学习、点位整改、研发介入或无需处理等操作建议。
11. 围绕平均法、Kalman、滑动窗口、Welford 等方案做数据实验和现场迭代。
12. 完成编译、打包、配置和部署脚本，降低现场使用门槛。

### Nav-Manager：车端闭环

1. 创建并持续迭代 `GoalCompensator` / `RunLearning` 相关类和数据结构。
2. 在任务成功结束后采集：
   - 目标点和前置点；
   - 载荷、楼层、坐标系、UUID；
   - 有码场景的示教姿态与相机偏差；
   - 无码场景补偿前、补偿后的控制误差；
   - 当前实际使用的补偿值。
3. 将不同误差统一成可供服务端计算的样本结构，并在无效数据时终止上传。
4. 从地图 `study_nodes` 解析多组补偿与示教数据。
5. 在任务初始化时按前置点、楼层、载荷和使用类型选择正确补偿。
6. 对有/无码模式处理 XY、Yaw 和坐标变换差异，修改实际目标位姿。
7. 保证补偿采集和补偿使用互不篡改，上传成功后重置 Case 状态。
8. 处理免示教、旧版本协议、层高传递、补偿类型和使用类型等兼容问题。
9. 修正到点精度判定，使判定基准与实际补偿后目标一致。
10. 让 `study_nodes` 随地图热更新进入运行态，并补足关键日志。

## 我获得了哪些产品经验

### 1. 从技术问题抽象产品目标

我把“某台车到点不准”提升为“同一业务场景下多车到点一致性和标定维护成本”的产品问题。解决方案不追求解释所有误差来源，而是用场景 Key 吸收耦合因素，直接优化最终到点结果。

### 2. 设计完整闭环，而不是孤立功能

我设计并实现了采集、同步、计算、审核、下发、应用、再采集的闭环。任何一段缺失，算法都无法形成长期产品能力。

### 3. 把场景差异建模成产品规则

前置点、载荷、楼层、有码/无码、坐标系和 UUID 不是单纯字段，而是决定“这份补偿能否复用”的业务条件。场景 Key 的设计本质上是产品边界设计。

### 4. 为高风险能力设计可控性

自动修改导航目标存在现场风险，因此产品必须有全局/点位开关、异常清理、置零、分发历史、自动流程恢复原状态和无效样本保护，而不能只追求自动化程度。

### 5. 用数据判断算法，而不是追逐算法名词

我对平均法、Kalman、Welford 等方法进行了样本回放和现场验证。Welford 实验发现 warm-up 离群点会让早期中心估计失真，因此继续设计稳定性判断、离群处理和停止条件。产品决策标准是精度、收敛轮次、稳定性和现场操作成本，不是哪种算法更“高级”。

### 6. 从功能交付走向可运营产品

我补充了 Web 操作、筛选、开关、一键流程、精度分析、处理建议、分发历史和部署脚本，使能力可以被实施和研发人员理解、控制和排查。

### 7. 在真实现场持续迭代

这项能力经历了多版本、多车型和多个现场变体。我的经验不是一次性做 Demo，而是在协议变化、字段不一致、数据量、锁、角度、层高和版本兼容问题中持续收敛产品。

## 目前可以讲的结果

- 已形成跨车端与服务端的完整自学习补偿闭环；
- 已支持有码/无码、前置点、载荷、楼层等场景区分；
- 已具备手动与自动操作、开关、清理、历史和精度分析能力；
- 稳定样本离线回放中，旧 5+5 方法估计中心的位置误差约 1.10 mm；
- Welford 方向仍处于实验迭代，不能描述为已经全面替代旧方法。

目前没有统一、可追溯的线上聚合数据证明整体业务提升，正式讲述不能声称“精度提升 X%”。

## 产品化定位与 AI 延展

这个项目不包装成高并发后端平台，也不把统计自学习直接描述为大模型 AI。更准确的定位是“面向 AGV/AMR 高精度对接场景的到点质量闭环产品”：

- 当前价值：把人工试跑和静态调参转化为可采集、可计算、可审核、可下发、可验证和可回退的长期闭环；
- 当前能力：确定性统计计算、跨系统工作流、风险控制和精度分析；
- Nav 内部 AI 首选方向：异常样本检测和收敛风险建议；
- 上层 AI 方向：正在开发的 AGV 云端运维平台负责多车趋势与异常事件，Diagnosis-Agent 结合日志、配置、SOP 和历史 Case 进行证据诊断；
- 安全边界：LLM 不直接计算、修改或下发补偿，所有高风险写操作必须经过规则校验和人工确认。

## 30 秒讲法

我主导开发了一套 AGV 到点自学习补偿产品，横跨服务端 `nav-application` 和车端 `nav-manager`。车端在真实任务结束后采集有/无码误差、载荷、楼层和点位上下文；服务端按场景分组估计误差中心，提供计算、审核、开关和下发；下一次任务再由车端匹配并应用补偿。我不仅做了前后端和导航接入，也把它从计算能力扩展成了可操作、可回退、可分析的现场产品。

## 事实边界

- 可以说“主导端到端开发和产品化落地”，因为有跨仓、前后端、工作流和长期迭代证据；
- 暂时不要说自己担任正式 PM，除非能补充正式职责或组织任命；
- 不把整个导航框架、控制器、MapMaster 或 Ops 说成个人开发；
- 二维码检码/补偿是相邻模块，只有与到点误差采集和补偿生效直接相关的部分纳入本项目；
- 二维码/激光定位源切换不是到点自学习主线，不放进核心讲述；
- Welford 和部分自动收敛方案仍在验证，不说成稳定量产结论。
