# 企业知识问答助手与 RAG 检索平台 PRD

> 产品名称：小迦
>
> 产品状态：2026年Q1完成自研版本开发并上线，2026年Q2进入交付使用与运营
>
> 目标用户：海外及工程团队
>
> 产品形态：独立、只读、可评测的企业知识问答服务

## 1. 项目背景

### 1.1 业务现状

海外及工程人员在AGV部署、实施和维护过程中，需要频繁查询产品规格、操作流程、配置方法、文档位置、版本差异和错误码说明。

相关知识已经沉淀在研发共享文档中，但用户经常不知道准确文档名称和内部术语。使用关键词搜索找不到答案后，只能在项目群中询问项目经理或研发人员，造成：

- 基础问题被重复回答；
- 工程人员等待人工回复，响应时间不稳定；
- 同一问题可能因回答人不同而口径不一致；
- 已有文档没有充分转化为可直接使用的答案；
- 海外和外包人员获得知识的成本更高。

### 1.2 前期验证

项目一期先使用钉钉知识助手快速上线试用，验证海外及工程团队是否愿意通过自然语言自助查询知识。

真实使用证明问答需求成立，同时暴露出三个突出问题：

1. 带合并单元格和多级表头的复杂表格解析后容易发生行列错乱；
2. 同一制度或产品资料存在多个版本时，旧版本可能优先被召回；
3. 外部网页知识缺少统一抓取、Markdown治理和原始链接回溯能力。

此外，钉钉阶段的检索过程难以拆解评测，也难以按公司产品需要提供独立问答服务。

### 1.3 产品判断

上述问题同时涉及知识接入、文档解析、检索策略、来源追溯、效果评测和产品集成，不能只依靠补充FAQ或调整Prompt解决。

因此先使用Dify搭建PoC，验证知识接入、检索生成、来源引用和无答案拒答链路；PoC验证可行后，进入定制化自研RAG建设。

## 2. 产品目标

### 2.1 业务目标

- 为海外及工程团队提供统一的知识问答入口；
- 提升产品知识、作业流程、文档资料和错误码信息的获取效率；
- 减少项目经理和研发人员反复回答基础问题；
- 将分散文档转化为可检索、可追溯、可持续维护的知识资产。

### 2.2 产品目标

- 支持问题补充、FAQ直答、RAG检索生成、来源引用和无答案拒答；
- 建立知识同步、清洗、切分、索引和检索全链路；
- 保留文档标题、章节、版本、权限和原始来源；
- 建立固定Golden Set、评测指标和Bad Case回归机制；
- 将RAG能力建设为可独立评测、可复用并可接入自有产品的服务。

### 2.3 首期成功标准

| 维度 | 成功标准 |
| --- | --- |
| 场景 | 四类核心知识问题能够通过统一入口处理 |
| 问题理解 | 信息不足时能够追问，不擅自补造条件 |
| 知识 | 1,000+篇有效文档完成治理并进入检索链路 |
| 回答 | 答案展示来源和适用条件，证据不足时拒答 |
| 评测 | 建立Golden Set并能够定位解析、召回、排序和生成问题 |
| 交付 | Q1完成上线，Q2面向海外及工程团队交付使用 |

## 3. 用户与场景

### 3.1 用户角色

| 用户 | 主要需求 | 产品价值 |
| --- | --- | --- |
| 海外工程人员 | 快速理解产品、部署和操作知识 | 降低语言、时区和人工响应成本 |
| 国内应用与实施人员 | 查询配置、标定、流程和错误码 | 减少跨文档搜索和重复咨询 |
| 外包工程人员 | 在授权范围内获得标准知识 | 在控制权限的前提下提升自助能力 |
| 项目经理与研发 | 减少基础问题打断 | 将精力集中在复杂问题和专业判断 |
| 知识负责人 | 维护文档、FAQ和版本 | 形成知识更新与质量闭环 |

### 3.2 四类核心问题

| 类型 | 典型内容 | 首选处理策略 |
| --- | --- | --- |
| 产品信息 | 产品规格、参数含义、指令和规则 | FAQ优先，未命中进入RAG |
| 作业流程 | 部署、配置、维护和标定步骤 | FAQ优先；受版本影响时进入RAG |
| 文档知识检索 | 文档位置、版本差异、跨资料综合知识 | RAG检索生成并展示来源 |
| 错误码 | 错误解释、已知问题和标准排查SOP | RAG提供知识指导，复杂诊断转人工 |

### 3.3 典型问题

- 某车型支持哪些导航或定位能力？
- 某项配置应该按照什么步骤完成？
- 新旧版本在参数或功能上有什么差异？
- 某个错误码表示什么，应该先检查哪些项目？
- 某份方案、会议结论或操作文档在哪里？

## 4. 产品范围

### 4.1 P0范围

- 自然语言提问；
- 问题完整性判断和必要上下文追问；
- 问题改写；
- FAQ匹配和标准答案直答；
- RAG检索、重排和答案生成；
- 文档名称、章节、版本和原始链接引用；
- 知识不足、来源冲突和无权限时拒答；
- 文本和表格知识接入；
- 文档同步、清洗、切分、索引和更新；
- 用户权限过滤；
- 问答记录、用户反馈和Bad Case分析；
- Golden Set离线评测和版本回归。

### 4.2 非目标

- 不连接车辆实时状态；
- 不读取现场日志或ROS Bag；
- 不执行终端命令；
- 不修改车辆配置；
- 不代替Diagnosis-Agent进行动态故障诊断；
- 不在首期进行全量图片OCR和视觉问答；
- 不对无充分知识证据的问题进行自由推断；
- 不因知识进入RAG而扩大用户原有访问权限。

## 5. 核心问答流程

用户提问
→ 判断问题是否完整
→ 必要时追问车型、版本、模块或具体对象
→ 在不改变原意的前提下改写问题
→ 匹配已审核FAQ
→ 未命中FAQ则进入RAG检索
→ 对候选证据进行融合、重排、去重和权限过滤
→ 判断证据是否充分、版本是否一致
→ 生成带来源答案或执行拒答
→ 用户查看引用并反馈
→ 进入知识或策略迭代

## 6. 功能需求

### FR-01：提交问题

用户通过统一入口输入自然语言问题。系统保存用户身份、问题文本、提交时间和会话上下文。

验收标准：

- 支持中文自然语言问题；
- 问题提交后展示处理状态；
- 每次请求具有唯一标识；
- 用户只能查看本人或授权范围内的记录；
- 系统异常时提供明确提示和重试入口。

### FR-02：判断问题完整性

系统判断回答问题是否需要车型、软件版本、模块、业务对象或其他必要条件。

验收标准：

- 信息完整时直接进入检索；
- 信息不足时只追问影响答案的必要条件；
- 存在多个业务对象时展示候选项供用户确认；
- 不得把模型猜测的车型、版本或对象写入检索问题；
- 用户补充信息后能够继续原会话。

典型Bad Case：“模板宽度怎么改”无法确定是库区模板、行为树模板还是其他模板，系统应先澄清对象。

### FR-03：问题改写

系统结合用户原问题和已确认上下文，生成适合检索的完整问题。

验收标准：

- 保留原始业务意图；
- 补入的条件必须来自用户确认或已有会话；
- 保留错误码、产品名称、版本号等关键实体；
- 改写结果支持回看和Bad Case分析；
- 改写失败时使用原问题检索或提示用户重新描述。

### FR-04：FAQ直答

系统优先匹配经过业务审核的高频标准问题。

每条FAQ至少包含：

- 标准问题；
- 常见表达；
- 标准答案；
- 适用车型和版本；
- 来源文档；
- 维护部门；
- 更新时间与状态。

验收标准：

- 高置信度命中时直接返回标准答案；
- 答案展示适用条件和来源；
- 低置信度或多个FAQ冲突时进入RAG；
- 未审核、已停用或版本不匹配的FAQ不得直答；
- FAQ命中和未命中状态写入问答记录。

### FR-05：RAG检索

系统使用关键词和向量两路召回，通过融合和重排获得最终证据。

验收标准：

- 关键词检索能够识别产品名、错误码、命令和专业术语；
- 向量检索能够处理自然语言与文档用词不一致的问题；
- 融合后保留足够候选结果进行重排；
- 最终证据经过权限过滤、去重和版本检查；
- 返回结果保留文档、章节、标题路径和来源链接；
- 检索过程可用于离线评测和Bad Case定位。

### FR-06：生成答案

模型仅依据通过检索和权限校验的知识证据回答。

验收标准：

- 核心结论与检索证据一致；
- 操作步骤保持顺序和必要前置条件；
- 多文档问题能够合并信息并保留各自来源；
- 版本相关回答明确展示适用车型或软件版本；
- 不添加知识证据无法支持的事实；
- 回答与引用一起返回。

### FR-07：来源引用

每条关键结论应关联能够支撑它的原始知识来源。

验收标准：

- 展示文档名称和章节；
- 保留原始链接并支持跳转；
- 外部知识使用真正提供证据的原始页面作为来源；
- 引用内容能够实际支持答案；
- 用户无权限访问的文档不得通过摘要或引用泄露；
- 来源失效时明确标记并进入治理清单。

### FR-08：无答案拒答

出现以下情况时系统不得强行作答：

- 知识库不存在相关内容；
- Top结果与问题弱相关；
- 核心证据缺失；
- 新旧版本资料互相冲突；
- 用户未补充必要上下文；
- 问题超出用户权限或产品范围。

验收标准：

- 说明无法回答的具体原因；
- 能够提示需要补充的信息；
- 可以展示相关但不足以支撑结论的资料；
- 配置修改、故障归因等高风险问题优先提示核验或转人工；
- 拒答原因进入Bad Case统计。

### FR-09：知识接入与清洗

系统将授权范围内的文本和表格知识同步至自研知识库。

验收标准：

- 正文可以稳定提取；
- HTML、转义字符和无关格式噪声得到清理；
- 标题、列表、代码块和链接得到保留；
- 合并单元格和多级表头按业务含义转换；
- 空文档、重复文档和解析失败文档能够识别；
- 失败文档进入重试或人工处理清单；
- 清洗结果可追溯至原文。

### FR-10：文档切分与索引

系统根据标题层级和内容结构切分文档，并建立全文与向量索引。

验收标准：

- Chunk保留文档标题和章节路径；
- 表格不因任意长度切分而丢失行列关系；
- 相邻上下文可以按规则扩展；
- 每个Chunk包含来源、版本、权限和更新时间；
- 新增或更新文档可以重新索引；
- 失效知识可以停止参与检索。

### FR-11：版本与时效管理

知识条目记录适用车型、软件版本、维护部门、更新时间和状态。

验收标准：

- 用户明确版本时优先检索匹配内容；
- 新旧版本同时命中时不得直接混合回答；
- 回答展示适用条件；
- 业务负责人可以标记有效、待复核或停用；
- 更新后触发重新清洗和索引；
- 历史版本仍适用于旧车型时可以保留。

### FR-12：权限控制

系统在检索前确定用户可访问的知识范围，并在召回、重排、生成和引用阶段持续执行权限控制。

验收标准：

- 未授权文档不能进入模型上下文；
- 用户不能通过提问推断受限知识；
- 外包和内部用户使用各自授权范围；
- 权限变更后能够及时生效；
- 权限过滤结果保留审计记录。

### FR-13：反馈与Bad Case

用户可以反馈回答无效、内容错误、版本过期、引用不符或仍需人工支持。

验收标准：

- 反馈与原问题、答案、引用和系统版本关联；
- 产品可以按问题类型和原因筛选；
- Bad Case能够归类为输入、知识、解析、召回、排序、生成、权限或系统问题；
- 处理后可使用原问题回归；
- FAQ、文档和检索策略的变更记录可追溯。

## 7. 知识治理

### 7.1 首期规模

首期聚焦海外及工程团队使用的研发共享知识，完成1,000+篇有效文档治理。

这里的1,000+指纳入治理并通过基础质量检查、能够进入检索链路的有效文档，不是原始文件抓取量，也不代表公司全部图文资产均已处理。

### 7.2 有效文档标准

- 来源明确且权限可确认；
- 正文非空、非重复；
- 标题、章节和表格结构可用；
- 原始链接和适用版本得到保留；
- 清洗、切分和索引成功；
- 能够参与检索并回溯原文；
- 业务内容由所属部门确认。

### 7.3 治理流程

知识盘点
→ 确认范围和负责人
→ 自动同步
→ 解析、清洗和去重
→ 恢复结构并补充元数据
→ 切分与索引
→ 抽检和Golden Set验证
→ 发布
→ 根据反馈更新

### 7.4 团队分工

| 角色 | 职责 |
| --- | --- |
| 产品经理 | 定义知识范围、有效标准、优先级、抽检和验收 |
| 研发 | 实现同步、清洗、切分、索引、更新和异常处理 |
| 知识负责人 | 确认业务正确性、适用版本、权限和时效 |

## 8. 评测与验收

### 8.1 Golden Set

按照四类高频业务问题各10道，并补充6道跨版本问题和6道跨文档链路问题，形成52道Golden Set。

每道题应包含：

- 原始问题和所属类型；
- 标准答案要点；
- 核心文档和核心证据Chunk；
- 适用车型或版本；
- 允许的辅助证据；
- 是否应该追问或拒答。

### 8.2 检索指标

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| Recall@5 | 每题Top 5命中的核心证据比例，再对问题取平均 | 衡量证据完整性 |
| Hit@5 | Top 5至少命中一条核心证据的问题比例 | 衡量是否找到正确方向 |

历史对照实验显示，加入Cross-Encoder重排后：

- Recall@5由约63%提升至约87%；
- Hit@5由约77%提升至约88%。

指标的历史实验与52道题证据边界见 [05-简历数据说明.md](05-简历数据说明.md)。

### 8.3 回答指标

| 指标 | 定义 |
| --- | --- |
| 问题回答率 | 给出有效答案的问题数÷进入统计的有效问题总数 |
| 回答准确率 | 人工审核正确的回答数÷进入评估的已回答问题数 |
| 引用正确率 | 引用能够实际支撑答案的回答比例 |
| 拒答准确率 | 应拒答问题中被正确拒答的比例 |
| 端到端时延 | 从用户提交到完整答案返回的时间 |

回答正确至少需要满足：

- 核心结论正确；
- 关键事实没有影响使用的遗漏；
- 车型和版本适用；
- 引用能够支撑结论；
- 没有证据外扩展。

### 8.4 Bad Case归因

| 层级 | 典型问题 | 处理方式 |
| --- | --- | --- |
| 输入 | 缺少车型、版本或对象 | 追问和问题改写 |
| 知识 | 文档不存在、过期或错误 | 补充、更新或停用知识 |
| 解析 | 表格错位、正文或标题丢失 | 修复清洗与结构化规则 |
| 召回 | 正确证据未进入候选集 | 优化关键词、同义词和向量召回 |
| 排序 | 正确证据在候选集但未进入Top 5 | 调整候选规模和重排 |
| 生成 | 证据正确但答案错误 | 优化提示、上下文和输出约束 |
| 权限 | 召回越权或引用不可访问 | 修复权限过滤 |
| 系统 | 超时、索引或调用失败 | 修复工程链路和降级 |

## 9. 上线与运营

### 9.1 阶段时间线

| 阶段 | 时间 | 主要结果 |

| 钉钉试用 | 2025年Q4 | 验证需求，收集真实问答和Bad Case |

## 10. 风险与应对

| 风险 | 影响 | 产品应对 |
| --- | --- | --- |
| 文档版本混淆 | 返回过期配置或操作方法 | 记录版本元数据，检索前过滤并展示适用条件 |
| 表格结构丢失 | 字段和数值错位 | 保留表头关系，建立复杂表格抽检 |
| 知识缺失 | 回答率下降或产生幻觉 | 正确拒答并进入知识补充清单 |
| 引用不能支撑答案 | 用户无法核验 | 评估引用正确率并关联原始章节 |
| 权限泄露 | 暴露内部知识 | 检索前过滤，生成和引用阶段二次校验 |
| 高风险答案错误 | 引发错误配置或操作 | 强制来源、版本提示和人工核验 |
| 指标虚高 | 无法反映真实价值 | 固定样本、知识版本、公式和审核记录 |

## 11. 产品经理职责边界

### 产品经理负责

- 分析历史问答、用户反馈和Bad Case；
- 定义目标用户、问题类型、MVP范围和非目标；
- 使用Dify搭建PoC，验证问答链路可行性；
- 设计问题追问、FAQ/RAG分流、引用和拒答规则；
- 制定文档有效性、结构化、版本和权限要求；
- 建立Golden Set、指标定义、验收标准和Bad Case机制；
- 协调业务、知识负责人和研发完成上线与运营。

### 研发负责

- 正式RAG架构和工程实现；
- 文档解析、切分、索引、召回、融合和重排；
- 模型、数据库和具体算法参数选型；
- 接口、权限、部署、监控、性能和稳定性；
- 根据评测结果完成技术优化。

### 共同决策

- 正式方案与PoC的差异；
- 效果、时延、成本和资源之间的取舍；
- 上线门槛和灰度范围；
- Bad Case的优先级和迭代节奏。
