# 企业知识问答助手与 RAG 检索平台：MVP 设计

> 本文档依据简历4整理，用于说明项目如何从钉钉需求验证、Dify PoC 走向定制化自研 RAG。项目讲述以产品判断、范围取舍和验收闭环为主，不把具体技术组件当作主线。

## 1. 一句话结论

项目采用三阶段推进：

1. **钉钉知识助手验证需求**：快速上线试用，验证海外及工程团队是否存在持续的知识问答需求，并收集真实问答与 Bad Case；
2. **Dify PoC 验证方案**：低成本跑通知识接入、检索、生成、引用和拒答链路，确认定制化 RAG 方向可行；
3. **自研 RAG 完成生产落地**：围绕文档解析、检索策略、来源引用、权限和产品集成进行定制建设。

最终落地不是直接使用 Dify，也不是从零训练大模型，而是由研发建设可控、可评测、可接入自有产品的 RAG 应用链路。

## 2. 为什么需要做这个项目

### 2.1 用户问题

海外及工程团队在 AGV 部署、实施和维护过程中，需要频繁查询：

- 产品规格、参数、指令和规则；
- 作业流程、配置和标定方法；
- 文档位置、版本差异和跨资料知识；
- 错误码解释与标准故障排查方法。

用户通常不知道准确文档名称和内部术语。通过关键词搜索找不到答案时，只能在项目群中询问项目经理或研发，造成重复咨询、响应不稳定和知识复用不足。

### 2.2 钉钉阶段验证了什么

一期使用钉钉知识助手快速上线试用，核心目标不是验证某种 RAG 架构，而是验证三个业务假设：

1. 工程人员是否愿意通过自然语言自助查询知识；
2. 高频查询是否能够由知识助手承接；
3. 真实使用中最影响答案质量的问题是什么。

历史问答量证明用户愿意使用知识问答入口；真实问答和 Bad Case 则暴露出复杂表格解析、上下文完整性、版本混淆、知识接入与检索可控性等问题。

### 2.3 为什么不能只优化钉钉助手

钉钉阶段主要存在以下限制：

- 合并单元格、多级表头等复杂表格解析后可能发生结构错乱；
- 同一制度或产品资料存在多个版本时，难以精细干预检索排序；
- 外部网页知识缺少统一抓取、Markdown 标准化和原始链接回溯能力；
- 检索链路难以拆解评测，无法准确区分解析、召回、排序和生成问题；
- 问答能力难以按产品需要作为独立服务接入公司自有产品。

这些问题同时涉及数据、检索、产品集成和运营闭环，不能只通过增加 FAQ 或修改 Prompt 解决。

## 3. 为什么先做 Dify PoC

### 3.1 PoC 要回答的问题

Dify PoC 只验证关键链路是否成立：

- 文档能否按自定义规则接入并形成知识库；
- 用户自然语言问题能否召回相关证据；
- 模型能否依据检索结果生成答案；
- 回答能否展示知识来源；
- 没有充分证据时能否拒答；
- 该能力是否值得进入定制化研发。

### 3.2 为什么不直接自研

项目早期最大的风险不是“研发能否实现”，而是：

- 用户需求是否真实且持续；
- 当前知识质量能否支持问答；
- RAG 能否明显改善搜索体验；
- 哪些能力必须定制，哪些可以复用现成组件。

使用 Dify 可以快速搭建可体验的链路，减少前期开发投入，并通过真实文档和问题暴露产品缺口。

### 3.3 PoC 的退出条件

当以下结论得到验证后，PoC 完成使命：

- 四类核心问题能够进入统一问答流程；
- 文档接入、检索和生成链路基本可用；
- 来源引用和无答案处理具有实现可行性；
- 低代码方案无法充分满足解析、重排、权限、评测和系统集成要求；
- 业务价值足以支持定制化研发投入。

因此，Dify 是方案验证工具，不是最终生产方案。

## 4. 自研 RAG MVP 的产品目标

首期目标是建立一个面向海外及工程用户的独立、只读知识问答服务，跑通以下闭环：

用户提问
→ 判断问题是否完整
→ 必要时追问并改写
→ FAQ 或 RAG 分流
→ 检索并判断证据是否充分
→ 返回带来源答案或拒答
→ 记录反馈和 Bad Case
→ 更新知识或检索策略

MVP 的成功不等于回答所有问题，而是做到：

- 在知识和证据充分时给出可靠答案；
- 在问题有歧义时先补充上下文；
- 在证据不足、版本冲突或超出权限时正确拒答；
- 回答能够追溯至原始文档和章节；
- 失败可以定位到知识、解析、检索、排序或生成环节。

## 5. 目标用户与问题范围

### 5.1 目标用户

- 海外工程人员；
- 国内应用、实施及技术支持人员；
- 经授权使用工程知识的外包人员；
- 知识维护人和产品运营人员。

### 5.2 四类核心问题

| 问题类型 | 典型问题 | 首选策略 |
| --- | --- | --- |
| 产品信息 | 产品规格、参数含义、指令和规则 | FAQ 优先，未命中进入 RAG |
| 作业流程 | 部署、配置、维护和标定步骤 | FAQ 优先；受车型或版本影响时进入 RAG |
| 文档知识检索 | 文档位置、版本差异、跨资料综合信息 | RAG 检索生成并提供来源 |
| 错误码 | 错误解释、已知问题和标准排查 SOP | RAG 提供知识指导，复杂诊断转人工 |

问题类型不等于固定技术路由。是否使用 FAQ 或 RAG，还需要根据答案稳定性、版本条件和上下文完整性判断。

## 6. MVP 功能范围

### 6.1 问题理解与改写

系统识别问题中是否缺少车型、软件版本、模块或具体对象。

- 信息完整：保留原意并生成适合检索的表达；
- 信息不足：先追问必要条件；
- 存在歧义：展示候选对象，由用户确认；
- 不允许系统补造用户未提供的事实。

例如，“模板宽度怎么改”可能指库区模板、行为树模板或动作模板，系统必须先确认对象再检索。

### 6.2 FAQ 直答

适用于高频、稳定且经过业务审核的标准问题。

每条 FAQ 至少包含：

- 标准问题及常见问法；
- 标准答案；
- 适用车型和版本；
- 来源文档；
- 维护部门和更新时间。

FAQ 命中后直接返回审核答案及来源，降低响应时延并避免稳定答案被生成模型改写错误。

### 6.3 RAG 检索生成

适用于需要查询原始文档、结合上下文或综合多份资料的问题。

产品要求：

- 同时利用关键词和语义相关性召回候选证据；
- 对候选内容进行融合、重排和去重；
- 保留标题路径、版本、来源和权限元数据；
- 仅依据通过权限检查的证据生成答案；
- 回答展示文档名称、章节和原始链接。

### 6.4 来源引用

引用不仅用于展示“参考资料”，还用于让用户验证：

- 答案来自哪篇文档；
- 证据位于哪个章节；
- 适用于什么车型或软件版本；
- 是否可以跳转原始来源查看完整上下文。

### 6.5 无答案拒答

出现以下情况时不强行回答：

- 知识库没有相关资料；
- 召回证据不足以支撑结论；
- 多份资料存在冲突；
- 用户没有补充必要上下文；
- 问题超出权限或产品能力边界。

拒答需要说明原因，并引导用户补充信息、查看相关文档或联系对应人员。

### 6.6 问答反馈与运营

保存问题、回答、引用、路由、耗时和用户反馈，用于：

- 识别无答案和错误答案；
- 区分知识缺失、解析失败、召回失败、排序失败和生成错误；
- 形成 FAQ 与文档补充清单；
- 使用固定测试集进行回归验证；
- 评估上线后的使用量和回答质量。

## 7. 知识范围与治理标准

### 7.1 首期知识范围

- 聚焦海外及工程团队使用的研发共享知识；
- 以文本和表格为主；
- 首期完成 1,000+ 篇有效文档治理；
- 图片内容不作为首期主要问答来源；
- 只接入用户原本有权限访问的知识。

### 7.2 有效文档标准

一篇文档被计入“有效文档”至少需要满足：

- 正文能够正常解析，非空且非重复；
- 具有明确标题、所属模块和原始来源；
- 保留目录层级、章节路径、表格和链接信息；
- 清洗后能够正常切分、索引并参与检索；
- 业务内容通过所属部门确认；
- 适用车型、版本或时效条件能够被识别。

### 7.3 知识治理流程

知识同步
→ 格式解析
→ 清洗与去重
→ 恢复标题和表格结构
→ 补充来源、权限及版本元数据
→ 文档切分
→ 建立索引
→ 抽检与检索验收
→ 发布

产品经理负责定义范围、标准、优先级和验收；研发负责自动化处理链路；知识所属部门负责业务正确性和版本审核。

## 8. MVP 评测设计

### 8.1 Golden Set

简历口径为 52 道问题：

- 产品信息 10 道；
- 作业流程 10 道；
- 文档知识检索 10 道；
- 错误码与故障排查 10 道；
- 跨版本问题 6 道；
- 跨文档链路问题 6 道。

每道题至少记录：

- 用户原始问题；
- 必要条件和答案要点；
- 核心文档；
- 计分核心证据 Chunk；
- 允许的辅助证据；
- 是否应该拒答；
- 适用车型和版本。

### 8.2 核心指标

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| Recall@5 | 每道题 Top 5 命中的核心证据比例，再对问题取宏平均 | 判断完整答案所需证据召回了多少 |
| Hit@5 | Top 5 至少命中一个核心证据的问题比例 | 判断问题是否找到了正确方向 |
| 回答准确率 | 人工判定正确的回答数 ÷ 已回答问题数 | 判断用户看到的答案是否正确 |
| 问题回答率 | 给出有效答案的问题数 ÷ 有效问题总数 | 判断系统能够承接多少问题 |
| 引用正确率 | 引用能够实际支撑答案的回答比例 | 判断答案是否可追溯 |
| 拒答准确率 | 应拒答问题中被正确拒答的比例 | 判断系统能否控制无依据回答 |
| 端到端时延 | 用户提交到获得完整答案的时间 | 判断实际使用体验 |

### 8.3 Baseline 与 Candidate

Baseline：

关键词检索＋BGE 向量检索
→ RRF 融合
→ 直接截取 Top 5

Candidate：

关键词检索＋BGE 向量检索
→ RRF 融合并保留 Top 20
→ Cross-Encoder Reranker
→ 输出 Top 5

Bad Case 分析发现，部分正确证据已经进入候选集，但没有排入 Top 5；因此增加 Reranker，目标是让真正能够支撑答案的证据进入最终上下文。

### 8.4 对外结果与证据边界

简历统一口径：

- Recall@5：63% → 87%；
- Hit@5：77% → 88%；
- 2026 年 Q2 累计完成 1,500+ 次问答；
- 覆盖 70 余名海外及工程用户；
- 问题回答率 93%；
- 回答准确率 85%。

当前证据边界：

- 63% → 87% 和 77% → 88% 来自历史 26 道独立问题的对照实验；
- 同一批 26 题分别运行 Baseline 和 Candidate，形成 52 条评测记录，但不等于 52 道独立题；
- “52 道 Golden Set”与历史检索结果尚需补齐逐题证据对齐，不能把两者混为同一次已验证实验；
- 线上回答率和准确率需要保留分子、分母、抽检方式和标注标准；
- 运营量能够证明真实使用，不能单独证明答案质量和业务效率。

## 9. MVP 验收标准

### 9.1 功能验收

- 四类核心问题能够进入统一问答入口；
- 问题存在歧义时可以追问并正确改写；
- FAQ 与 RAG 能够按规则分流；
- 文本、表格和来源元数据可以进入知识链路；
- 回答能够展示原始文档及章节；
- 证据不足时能够拒答；
- 问答记录支持 Bad Case 定位和回归。

### 9.2 效果验收

- 使用冻结的问题集和知识版本比较 Baseline 与 Candidate；
- 分别评估普通题、跨版本题和跨文档题；
- 检查检索证据是否完整，而不是只看答案是否“像是正确”；
- 回答正确性和引用支撑性由人工独立审核；
- 高风险问题即使能够回答，也必须展示版本、来源和核验提示。

### 9.3 上线边界

首期是只读知识助手：

- 不连接车辆实时状态；
- 不读取现场日志；
- 不执行终端命令；
- 不修改车辆配置；
- 不替代 Diagnosis-Agent 进行动态故障诊断；
- 配置修改、故障归因等高风险内容要求用户核验来源或转人工。

## 10. 版本推进

### 阶段一：钉钉试用

- 快速建立知识问答入口；
- 面向海外及工程团队开放试用；
- 收集真实问答、无答案问题和用户反馈；
- 验证需求成立并识别平台限制。

### 阶段二：Dify PoC

- 接入代表性文档；
- 跑通知识检索、生成、来源引用和拒答；
- 使用典型 Bad Case 验证自定义链路的改善空间；
- 明确定制研发范围和首期验收目标。

### 阶段三：自研 RAG MVP

- 建立知识同步、清洗、切分、索引和检索链路；
- 实现问题改写、FAQ/RAG 分流、来源引用和无答案处理；
- 完成 1,000+ 篇有效文档治理；
- 建立 Golden Set、指标和 Bad Case 回归机制；
- 验收通过后上线运营，并为接入自有产品提供独立服务。

## 11. 个人职责与团队边界

### 产品经理主责

- 分析历史问答和 Bad Case，定义用户、场景和 MVP；
- 使用 Dify 搭建 PoC，验证产品流程和方案可行性；
- 设计问题改写、FAQ/RAG 分流、来源引用和拒答规则；
- 制定文档有效性、结构化和版本治理标准；
- 建立 Golden Set、指标口径和 Bad Case 分类方法；
- 协调业务、研发和知识负责人完成治理、验收和上线。

### 研发主责

- 正式 RAG 架构与工程实现；
- 文档解析、切分、索引、召回、融合和重排；
- 模型、数据库及具体算法参数选型；
- 接口、权限、部署、监控、性能和稳定性；
- 根据评测和 Bad Case 完成技术优化。

产品经理需要关注最终落地形式，因为它影响集成、权限、质量、成本和运营；但产品经理负责提出约束和验收目标，与研发共同完成选型，而不是独自决定具体技术框架。

## 12. 面试口述版

这个项目不是一开始就直接自研 RAG，而是分三步验证。

第一步，我们先基于钉钉知识助手快速上线试用，验证海外和工程团队是否真的愿意用自然语言查询知识。真实问答说明需求成立，但也暴露了复杂表格解析、版本文档召回、外链知识接入和检索不可评测等问题。

第二步，我基于 Dify 搭建 PoC，用代表性文档和 Bad Case 跑通知识接入、检索、生成、来源引用和拒答，确认定制化 RAG 方案可行。Dify 的作用是低成本验证，不是最终生产方案。

第三步，我们建设自研 RAG MVP。我将首期范围收敛为四类工程知识问题，设计问题补充、FAQ 直答、RAG 检索生成、来源引用和无答案拒答，并制定有效文档和版本治理标准，推动完成 1,000+ 篇文档治理。同时建立 Golden Set 和 Bad Case 评测机制，推动检索和重排策略优化。

我的核心贡献是把钉钉阶段的真实问题转化为自研产品的范围、规则和验收体系，并协调研发和业务完成知识治理、效果验证及上线，而不是开发底层检索算法。
