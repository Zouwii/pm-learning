# 企业级 RAG 落地项目：AI 产品经理职责与能力边界

> 用途：明确 AI 产品经理在企业级 RAG 项目中的职责、能力要求和团队边界，用于简历梳理与面试回答。

## 一、核心定位

AI 产品经理不需要亲自训练模型或开发检索引擎，但需要把以下链路串成闭环：

`业务问题 → 知识数据 → 产品方案 → 技术选型 → 评测验收 → 上线运营 → Bad Case 迭代`

最核心的价值不是复述算法名词，而是回答：

- 为什么要做 RAG；
- 为谁解决什么问题；
- 什么知识可以回答；
- 什么结果算正确；
- 达到什么标准可以上线；
- 上线后如何持续优化。

## 二、AI 产品经理应主导的工作

### 1. 业务场景与产品目标

需要明确：

- 哪些用户在什么场景下使用；
- 当前查找知识的主要问题是什么；
- 首期覆盖哪些知识域；
- 哪些问题应该回答，哪些问题应该拒答；
- RAG 相比 FAQ、传统搜索或人工支持的价值是什么；
- 如何衡量业务价值和产品效果。

在企业知识问答项目中，典型场景是海外及工程团队查询产品、流程、技术文档和故障知识。一个问题的答案可能分散在多篇文档中，还可能受到产品型号、软件版本和适用环境影响。

### 2. 历史问题与 Bad Case 分析

AI 产品经理应重点负责：

- 分析历史问答和用户反馈；
- 合并语义和业务意图相同的不同问法；
- 建立业务问题分类和难度分类；
- 识别漏召回、错误召回、证据不完整、版本混淆和生成错误；
- 判断问题发生在知识、检索、排序、生成还是交互环节；
- 将问题转换成可执行的产品或技术优化需求。

不能只说“模型效果不好”，而要说明：

`哪类问题 → 为什么失败 → 影响什么指标 → 应优化哪个环节`

### 3. 知识治理标准

产品经理不需要亲自清洗全部文档，但应定义知识接入和治理规则：

- 哪些文档允许进入知识库；
- 什么是有效文档；
- 产品、型号、模块、版本和时间等元数据如何标注；
- 重复、过期和互相冲突的文档如何处理；
- 表格、图片、附件和外链如何接入；
- 文档如何切分并保留标题和上下文；
- 谁负责更新，多久同步一次；
- 如何控制文档访问权限。

知识治理的目标不是单纯增加文档数量，而是保证知识可解析、可检索、可判断版本、可追溯和可持续更新。

### 4. Golden Set 与评测体系

这是 RAG 项目中最能体现 AI 产品经理价值的部分之一。

AI 产品经理需要推动：

- 从真实历史问题中选择评测题；
- 设计业务类型和难度分布；
- 标注核心文档和计分核心 Chunk；
- 定义 Recall@5、Hit@5、答案准确率和引用准确性；
- 区分检索评测、生成评测和拒答评测；
- 冻结评测语料、问题和标注口径；
- 制定上线验收标准；
- 组织对照实验和 Bad Case 复盘。

算法团队可以执行实验，但“用什么题、什么算正确、达到什么标准可以上线”应由产品、业务和技术共同确定，产品经理负责推动形成统一口径。

### 5. 产品功能与问答策略

需要设计用户真正使用的产品闭环：

- FAQ 直答与 RAG 问答如何分流；
- 答案如何展示来源和引用；
- 无答案时如何拒答；
- 条件不足时如何向用户追问；
- 多轮问答如何保留上下文；
- 如何跳转并查看原文；
- 用户如何反馈答案是否有效；
- 错误答案如何进入 Bad Case；
- 权限不足的文档如何过滤；
- 响应时间过长时如何展示过程和降级。

### 6. 技术方案的产品决策

AI 产品经理不一定负责工程实现，但需要理解主要技术环节及其业务影响：

- 关键词检索和向量检索各自适合什么问题；
- 为什么需要 Hybrid Retrieval 和 RRF 融合；
- Reranker 解决什么问题，又不能解决什么问题；
- Chunk 大小如何影响语义完整性和召回精度；
- Top K 如何影响召回率、延迟和成本；
- 元数据过滤如何解决型号、版本和权限问题；
- Query 改写与问题拆解适合哪些复杂问题；
- 为什么召回正确证据不代表生成答案一定正确。

产品经理的任务是把技术选择与业务问题连接起来，并在效果、成本、延迟、复杂度和交付周期之间做取舍。

### 7. 上线验收与运营迭代

上线前需要确认：

- 核心场景是否达到验收指标；
- 权限、引用、拒答和异常流程是否完整；
- 响应时间和系统稳定性是否可接受；
- 是否具备日志、反馈和问题追踪能力。

上线后需要持续关注：

- 问答量、用户数和活跃情况；
- 问题回答率和答案准确率；
- 响应时间和失败率；
- 无答案问题、负反馈和人工转交；
- 新增知识需求和知识过期情况；
- Bad Case 类型及变化趋势；
- 每轮优化前后的同集对照结果。

## 三、能力要求

### 1. 业务与产品能力

- 能识别高价值、高频且适合 RAG 的场景；
- 能把模糊需求转化为明确的产品范围和验收标准；
- 能设计问答、引用、追问、拒答和反馈闭环；
- 能平衡用户体验、效果、成本和交付周期。

### 2. 数据与知识能力

- 能设计文档分类、元数据和版本体系；
- 能识别知识缺失、冲突、重复和过期问题；
- 能定义 Chunk 标注和答案证据标准；
- 能组织业务专家完成评测数据标注。

### 3. AI 与 RAG 基础能力

需要能够解释并应用以下概念：

- Embedding 与向量相似度；
- 关键词检索、向量检索和混合检索；
- RRF、Top K 和 Reranker；
- Chunk、父子分块和结构化切分；
- Recall、Hit、MRR、nDCG；
- Query 改写、问题拆解和多跳检索；
- 幻觉、引用、拒答和答案忠实度。

理解深度应达到：能够根据 Bad Case 判断问题可能发生在哪一环，并与算法和研发共同讨论方案，而不只是记住术语定义。

### 4. 实验与分析能力

- 能设计 Baseline 和 Candidate 对照实验；
- 能保证测试集、语料和指标口径一致；
- 能区分百分点提升与相对提升；
- 能从平均指标下钻到具体问题；
- 能根据 Bad Case 判断下一轮优化优先级；
- 能识别指标提升是否真正改善用户体验。

### 5. 项目推动能力

- 协调业务专家、算法、后端、前端和测试；
- 明确不同团队的交付物和验收责任；
- 控制知识治理、研发、评测和上线节奏；
- 管理效果、性能、成本和安全风险；
- 推动实验结论真正进入产品，而不是停留在 PoC。

## 四、与技术团队的能力边界

| 责任层级 | AI 产品经理的合理表述 |
| --- | --- |
| 我主导 | 场景分析、需求设计、知识标准、Golden Set、指标口径、验收规则、Bad Case 分析、产品功能和上线运营 |
| 我参与 | 检索方案讨论、实验设计、模型与参数取舍、实验结果分析、优化优先级和技术风险评估 |
| 技术团队负责 | 检索服务开发、Embedding 与 Reranker 部署、索引构建、接口开发、性能优化和工程实现 |

### 可以说

- “我构建了 Golden Set 并定义验收指标。”
- “我基于 Bad Case 识别问题并推动检索策略优化。”
- “我与算法团队共同确定混合检索和重排方案。”
- “我设计了来源引用、拒答和用户反馈闭环。”
- “我推动方案从 PoC 进入上线验收和运营迭代。”

### 谨慎说

- “我开发了 RAG 检索引擎。”
- “我训练了 Embedding 或 Reranker 模型。”
- “我实现了向量数据库和检索算法。”
- “指标提升完全由我个人实现。”

除非确实承担了对应开发工作，否则这些表述会把面试追问引向模型训练、算法实现和系统工程细节。

## 五、面试核心回答

### Q1：AI 产品经理在 RAG 项目里具体负责什么？

> 我主要负责把业务问题转化为可落地、可评测的 RAG 产品方案。前期会分析用户场景和历史问题，明确知识范围和首期目标；中间负责制定知识治理标准、设计问答和引用等产品能力，并构建 Golden Set、定义评测指标和验收标准；实验阶段基于 Bad Case 与算法和研发共同确定优化方向；上线后持续跟踪问答效果、用户反馈和知识更新，形成运营迭代闭环。

### Q2：你和算法工程师的分工是什么？

> 我负责定义问题、数据标准、评测方法、产品方案和验收目标，并根据 Bad Case 判断优化优先级；算法工程师负责检索、重排和模型服务的具体实现。技术方案不是完全割裂的，我需要理解混合检索、Reranker 和 Chunk 等机制，才能与算法团队共同判断某个方案是否值得做，但不会把底层实现描述成我的个人开发成果。

### Q3：为什么评测体系应该由产品经理参与？

> 因为 RAG 的正确性不是纯技术问题。哪些问题有业务价值、哪些文档是权威来源、什么证据足以支撑答案、版本错误是否可以接受，都需要业务判断。如果只由技术团队根据相似度评估，很容易出现指标看起来提升，但实际答案不适用的情况。产品经理需要把业务正确性转化成可标注、可计算和可验收的标准。

### Q4：产品经理需要懂多深的技术？

> 不一定要能够训练模型或编写检索服务，但必须理解完整链路，能够解释关键词检索、向量检索、RRF、Reranker、Chunk和核心评测指标，并能根据 Bad Case 判断问题在知识、召回、排序、生成还是交互环节。技术理解最终要服务于产品决策和跨团队协作。

### Q5：你在这个项目中的价值是什么？

> 我的价值不是单独提出某个算法，而是建立了一套从真实问题、知识标注、离线评测、Bad Case归因到上线验收的闭环。这样团队不再凭主观感受判断模型效果，而是能够用统一数据定位问题、比较方案并持续迭代。

## 六、一句话定位

> 我不是负责训练模型或开发检索引擎，而是负责定义业务问题、建立知识和评测标准、分析 Bad Case，并与算法和研发共同确定优化方案和验收结果，最终推动 RAG 能力形成可上线、可评估、可持续迭代的产品闭环。

## 七、自查清单

面试前确认自己能清楚回答：

- 为什么该场景适合使用 RAG？
- Golden Set 如何构建，什么算正确答案？
- Recall@5 和 Hit@5 分别说明什么？
- 为什么 Baseline 效果不足？
- Bad Case 如何归类并转化成优化动作？
- Reranker 能解决什么，不能解决什么？
- 检索正确为什么不代表答案正确？
- 知识版本、权限和更新如何管理？
- AI 产品经理与算法、研发如何分工？
- 上线后如何评估业务价值并持续迭代？
