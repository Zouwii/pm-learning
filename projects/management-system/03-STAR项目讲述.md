# 研发知识库 RAG V2：STAR 项目描述

> 对外单线版本：只讲基于真实知识资产建设的 RAG V2，不展开其他管理模块。实验指标使用占位符，真实结果产出后替换。

## 项目定位

这是一个面向研发新员工和跨模块协作人员的内部知识库 RAG 问答项目。项目围绕约 55G 原始图文知识资产，首期重点处理 5,427 份 Markdown 和其中的文本、表格与链接信息，通过结构化数据治理、Hybrid RAG、重排和带引用生成，帮助用户查询研发项目、任务方案、项目节点、验收资料和模块文档。

## 我的角色

我负责项目从问题定义、范围收敛、数据策略、RAG 方案到评测设计和核心实现的端到端工作：

- 定义目标用户、核心问题和首期知识范围；
- 设计数据清洗、切分、索引、检索、重排和问答链路；
- 建立数据、检索、回答与性能四层评测；
- 基于实验结果和 Bad Case 确定迭代优先级与最终方案。

## S：Situation，背景

研发项目资料长期分散在多个钉钉知识空间和模块文档中，包含技术方案、项目计划、任务背景、验收记录、接口说明和版本资料。新员工或跨模块协作人员遇到问题时，往往不知道准确文档名和内部术语，只能反复搜索、逐篇阅读或询问熟悉业务的同事。

原生关键词搜索能够找到包含特定词汇的文档，但难以处理自然语言与内部术语不一致、多份资料需要综合、表格和长文档结构复杂等问题，也不能直接给出带来源依据的答案。

已有小迦还存在数据接入限制：包含外部链接的文档无法存入知识库。这意味着部分真实存在的研发资料无法进入检索和问答链路，形成知识覆盖缺口。此类问题的根因在数据接入层，不能只依靠 Prompt、召回或重排优化解决。

公司已有约 55G 原始图文知识资产，其中盘点出 5,427 份 Markdown 和 19,886 张图片。真正的挑战不是“有没有数据”，而是怎样把这些异构、长短不一、结构复杂的资料转化为可检索、可评测和可追溯的知识问答能力。

历史使用数据也验证了知识问答需求。2025 年 Q4，群助理累计 903 次问答、72 人提问，记录 81 次“答案不符-待更新”，占比 9%；小迦累计 1,381 次问答，其中访客来源 918 次、占 66%，记录 21 次“答案不符-待更新”，占比 2%。2026 年 Q2，群助理累计 768 次问答、70 人提问，记录 55 次答案不符，占比约 7%；小迦累计 1,531 次问答、79 人提问，但没有继续统计答案不符。

两个季度的总问答量分别为 2,284 次和 2,299 次，整体保持稳定；小迦问答量增长约 10.86%，群助理下降约 14.95%。这些数据说明用户存在持续的知识问答需求，同时也暴露出质量指标口径不完整的问题，因此后续不能只看问答量，需要补充标准测试集、检索指标和回答质量评测。

自主 RAG 计划统一承接原群助理和小迦两个入口。按照历史合计问答量估算，季度承接规模约为 2,300 次问答。该数字是迁移用量估算，不是自主 RAG 上线后的独立埋点数据。

> 数据边界：两个渠道的用户可能重叠，不能直接合并为独立用户数；“答案不符-待更新”的统计来源尚未确认，不能直接换算为回答准确率；2025 Q4 的“访客 918”是原始来源字段，不视为独立用户数；小迦在 2026 Q2 没有对应质量数据。

## T：Task，任务

我的目标是从 0 到 1 建设研发知识库 RAG 问答产品，并解决五个问题：

1. 明确首期服务哪些用户问题，避免把 55G 数据规模本身当成产品目标；
2. 保证 Markdown 正文、标题层级、表格、链接和来源信息在清洗与切分中不丢失；
3. 兼顾模块名、版本号等精确词汇与自然语言语义查询；
4. 让回答携带可核验来源，资料不足或冲突时能够拒答或提示确认；
5. 建立独立真实问题集，用统一 baseline/candidate 实验证明方案效果。

## A：Action，行动

### 1. 从数据规模收敛到真实用户问题

我没有把首期目标定义为“处理全部 55G 多模态数据”，而是先聚焦三类高价值问题：

- 项目、任务和方案检索；
- 项目节点、验收和版本资料查询；
- 模块设计、接口和配置文档查询。

首期优先使用 5,427 份 Markdown 中的文本和表格信息，19,886 张图片保留原文回链。只有 Bad Case 证明图片缺失是主要瓶颈时，再投入 OCR 或多模态能力。

### 2. 建立可追溯的数据治理链路

我先处理上游数据质量，而不是直接调 Prompt：

- 清理 Markdown 中影响正文的 HTML、转义、噪声和失效结构；
- 保留标题、列表、表格、代码、链接和图片占位信息；
- 保存 workspace、node、文档标题、标题路径、更新时间和内容版本；
- 使用 checksum 支持幂等同步和受影响文档的定向重建；
- 用固定 canary 文档比较 baseline 与 candidate，防止修复一种格式时破坏另一种格式。

### 3. 使用结构感知的 parent-child chunking

针对研发文档篇幅长、标题层级深、表格密集的问题，我采用基于 Markdown outline 的 parent-child chunking：

- parent 保存章节语义和标题路径；
- leaf 控制检索粒度与 token 上限；
- 检索命中 leaf 后回扩相关 parent，为模型提供完整上下文；
- 对表格按行组切分，并保留表头和所属章节；
- 对标题前正文、超长段落和短碎片设置专门的合并与保护规则。

这样既避免整篇文档直接 embedding 导致语义过宽，也减少固定长度切分造成的上下文断裂。

### 4. 搭建 Hybrid RAG 与带引用问答

检索侧采用两路召回：

- FULLTEXT / FTS 处理模块名、版本号、接口名和精确术语；
- bge embedding + pgvector 处理自然语言表达和语义近似查询；
- 使用 RRF 融合两路结果，降低单一召回方式的偏差；
- 使用 Cross-Encoder reranker 对候选结果重排；
- 对重复 chunk 做合并，并扩展必要的父级上下文。

生成侧要求模型基于检索证据回答并展示文档标题、章节和来源链接。没有足够材料时输出信息缺口；多份资料冲突时并列展示来源，不让模型自行选择一个“看起来正确”的公司事实。

### 5. 建立四层评测与 Bad Case 闭环

我将评测拆成四层，避免只用一个 Recall 指标代表整个产品：

| 层级 | 评测内容 |
| --- | --- |
| 数据与解析 | 文档成功率、正文保留率、表格完整率、空文档和重复文档 |
| 检索 | Recall@5、MRR、nDCG@5 |
| 回答 | 引用正确率、事实一致率、拒答准确率 |
| 性能与产品 | P50/P95 延迟、问题完成率、来源点击和用户反馈 |

测试问题从真实研发查询场景中获得，不根据已选文档反向编造；冻结语料版本和独立测试集后，在同一数据上比较 baseline 与 candidate。

每个 Bad Case 归类到数据缺失、清洗、切分、召回、排序或生成层，再决定修改数据规则、chunking、检索策略还是回答约束，避免用 Prompt 掩盖上游问题。

### 已有历史检索指标：v4 精简答案口径

v4 使用 26 道独立问题，分别完成无重排和有重排两组 Top 5 测试，共形成 52 条离线评测记录。它是对 v1 检索输出重新计分，不是重新训练或更换模型。评价时每题最多要求召回 2 个核心证据 chunk，共计 46 个必需证据位。

| 指标 | 无重排：Hybrid RRF | 有重排：Hybrid RRF Top 20 + bge-reranker-base |
| --- | ---: | ---: |
| Recall@5（宏平均） | 63.46% | **86.54%** |
| 整体核心证据召回 | 63.04%（29/46） | **86.96%（40/46）** |
| 完整召回率 | 50.00%（13/26） | **84.62%（22/26）** |
| 问题命中率 Hit@5 | 76.92%（20/26） | **88.46%（23/26）** |
| MRR | 55.90% | **69.68%** |
| nDCG@5 | 52.12% | **72.45%** |

面试口述时可概括为：我围绕 26 道独立问题完成无重排和有重排两组实验，形成 52 条离线评测记录。加入轻量 Cross-Encoder 重排后，Top 5 核心证据召回率从约 63% 提升到约 87%，完整覆盖问题由 13 题提升到 22 题，问题命中率达到 88.46%。最终选择约 280 MB 的 `bge-reranker-base`，历史服务器记录约 1 秒/题，效果略低于大模型方案但部署性更好。

> 边界：以上是 v1 检索结果按 v4 口径复评，不是当前 V2 leaf 链路指标，也不是回答准确率。

## R：Result，结果

1. 完成约 55G 原始知识资产盘点，首期覆盖 5,427 份 Markdown，建立文本、表格和来源回链的数据处理方案；
2. 完成 Markdown 清洗、outline parent-child chunking、全文与向量混合检索、RRF 融合、Cross-Encoder 重排和带引用问答主链路；
3. 构建 26 道独立真实问题，覆盖技术文档 10 题、会议纪要 7 题、跨文档问题 5 题和表格问题 4 题；通过 TREC Pooling 汇总候选，并使用 `deepseek-v4-pro` 辅助相关性标注；分别完成无重排和有重排两组实验，共形成 52 条离线评测记录；
4. 按每题最多 2 个核心证据 chunk 的 v4 口径复评，加入 reranker 后，Recall@5 宏平均从 63.46% 提升到 86.54%，整体核心证据召回从 63.04%（29/46）提升到 86.96%（40/46）；
5. 完整召回率从 50.00%（13/26）提升到 84.62%（22/26），问题命中率 Hit@5 从 76.92%（20/26）提升到 88.46%（23/26），MRR 从 55.90% 提升到 69.68%，nDCG@5 从 52.12% 提升到 72.45%；
6. 向量召回使用 `BAAI/bge-small-zh-v1.5`（512 维），重排最终选择 `BAAI/bge-reranker-base`（约 280 MB），整体链路为 `FULLTEXT + bge-small → RRF Top 20 → bge-reranker-base → Top 5`。虽然 `BAAI/bge-reranker-v2-m3`（约 2.2 GB）的历史 Recall@5 略高，但 `base` 在检索效果、响应速度和部署资源之间更均衡；
7. 历史服务器记录显示 `bge-reranker-base` 平均约 1 秒/题；据此估算，检索链路 P95 从无重排约 **0.5 秒**增加到有重排约 **1.5 秒**。最终接受约 1 秒的额外检索等待，以换取核心证据 Recall@5 从约 63% 提升到约 87%；该 P95 为规划估算值，不是独立压测结果；
8. 自主 RAG 计划统一承接原群助理和小迦入口，按照 2025 Q4 与 2026 Q2 的历史合计问答量估算，季度承接规模约 2,300 次问答。该数字是迁移用量估算，不是自主 RAG 上线后的独立埋点结果；
9. 基于重排后 Hit@5 为 88.46% 进行效果估算：假设正确证据进入 Top 5 后，模型正确引用并使用证据的概率约为 90%～95%，引用内容支撑率预计约 80%～84%，取中间值约 **82%**，目标设为 **85%**；
10. 同样按照“正确证据命中 88.46% × 命中后成功生成可用答案 85%～90%”估算，真实用户问题完成率预计约 75%～80%，取中间值约 **77%**，目标设为 **80%**。如高频问题继续由 FAQ 兜底，FAQ+RAG 综合完成率可预估为 **80%～85%**；
11. 上述 P95、引用支撑率和问题完成率均为基于历史耗时或离线召回结果的规划估算值，尚未经过线上逐题人工审核、独立压测或埋点验证，不能对外描述成已实现的真实线上指标。

## 2 分钟口述模板

我负责建设一个面向研发新员工和跨模块协作人员的内部知识库 RAG 问答产品。公司已有约 55G 原始图文知识资产，其中包括 5,427 份 Markdown 和 19,886 张图片，但资料分散、结构复杂，用户通常不知道准确文档名和内部关键词，原生搜索很难直接回答项目方案、验收节点和模块知识问题。

我先把范围收敛到项目任务与方案、项目节点与验收、模块设计文档三类场景。首期重点处理 Markdown 文本和表格，图片保留回链。数据层先做结构保真的 Markdown 清洗和版本元数据，再使用基于标题层级的 parent-child chunking，兼顾检索粒度和完整上下文。检索层采用全文与向量双路召回、RRF 融合和 Cross-Encoder 重排，回答必须展示来源，材料不足或冲突时明确拒答或提示核验。
