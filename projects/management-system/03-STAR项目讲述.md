## S｜Situation

### S1：旧知识查询流程

#### 1. 核心用户与相关角色

- 核心用户：参与 AGV 部署实施的国内外工程人员；
- 人工兜底方：项目经理和研发人员；
- 外包用户：同样存在工程知识查询需求，钉钉阶段通过访客机制使用知识助手。

#### 2. 已知的四类查询需求

工程人员在部署、实施和维护过程中，主要查询以下四类信息：

1. 产品信息、指令与规则；
2. 作业流程、配置和标定方法；
3. 文档知识与跨资料综合信息；
4. 错误码解释及标准故障排查方法。

#### 3. 原有处理流程

```text
工程人员在现场遇到知识问题
→ 根据经验查找共享文档或使用关键词搜索
→ 找到资料后自行理解和执行
→ 找不到、无法确认或需要综合多份资料时，在项目群中提问
→ 项目经理或研发结合文档和个人经验人工答复
```

#### 4. 旧流程痛点

**对工程人员：**

- 不一定知道准确的文档名称和内部术语；
- 自然语言描述与文档中的关键词可能不一致；
- 即使资料存在，也可能需要查找和阅读多份文档；
- 自助查找失败后依赖人工答复，响应时间不可控。

**对项目经理和研发：**

- 需要重复回答产品参数、操作步骤和常见错误码等基础问题；
- 工作容易被现场即时咨询打断；
- 人工答案依赖个人经验，不同人员的回答可能不一致。

**对公司知识资产：**

- 已有文档没有充分转化为一线人员可快速获取的答案；
- 同类问题反复出现，人工答复没有形成稳定的自助闭环。

### S2：钉钉知识助手上线及运营表现

#### 1. 上线目的

为了减少工程人员对项目经理和研发的重复咨询，公司基于钉钉平台上线知识助手，让用户通过自然语言查询已有工程知识。

#### 2. 产品形态

钉钉阶段通过知识助手“小迦”为用户提供独立的知识问答入口；公司内部工程人员使用组织内账号，外包用户通过访客机制访问。

#### 3. 2025 年 Q4 运营数据

| 产品入口 | 问答量 | 用户数据 | 无回答问题 |
| --- | ---: | ---: | ---: |
| 小迦 | 1,381 次 | 918 次访客来源 | 21 次 |

#### 4. 运营结论

- “小迦”单季度累计承接 1,381 次问答，说明工程团队存在持续的知识查询需求；
- 用户愿意通过问答产品自助获取知识，产品方向得到初步验证；
- 21 个无回答问题说明现有知识覆盖和问答链路仍有完善空间；
- 仅统计问答量和无回答问题，无法判断问题具体出在知识缺失、文档解析还是检索环节。

#### 5. Bad Case 暴露的问题

结合历史问答和 Bad Case，主要发现：

1. 表格和复杂文档结构解析不完整；
2. 部分包含外部链接的知识无法接入；
3. 检索链路不可拆解，难以判断失败发生在哪个环节；
4. 检索策略受平台限制，无法根据业务特点持续优化；
5. 钉钉内的问答能力难以作为独立服务接入公司自有产品。

#### 6. 阶段判断

钉钉知识助手已经验证了“工程人员愿意使用知识问答产品”，但无法满足后续对知识覆盖、检索效果、质量评测和产品集成的要求，因此需要进一步评估自建 RAG 方案。

### S3：从运营问题到自建 RAG 需求

#### 1. 用户问题理解

工程人员通常直接使用现场语言提问，问题可能缺少车型、版本、模块或具体对象。例如“如何在模板中修改宽度”，无法确定用户指的是哪一种模板。

因此，产品不能直接对所有问题执行检索，而需要：

```text
识别问题是否完整
→ 信息不足时追问必要上下文
→ 根据用户补充内容改写成完整问题
→ 使用完整问题进行检索
```

问题改写不能擅自补充用户没有提供的信息；存在歧义时，需要先让用户确认。

#### 2. 钉钉文档解析与清洗

原始知识主要来自钉钉文档，文档中可能包含：

- HTML 和转义字符；
- 表格、列表、代码块和外部链接；
- 空内容、重复内容或失效结构；
- 不同文档格式转换后产生的噪声。

如果直接进入知识库，可能造成正文缺失、表格含义破坏或无效内容参与检索。因此需要建立文档清洗和结构化标准，再将有效内容送入索引。

#### 3. 文档目录层级

工程文档通常篇幅较长，同一个术语可能出现在不同章节。如果切分时只保留局部文本，不保留目录层级，系统会丢失这段内容属于哪个产品、模块和操作步骤。

知识处理需要保留：

- 文档标题；
- 一级、二级等目录标题；
- 当前内容所在的标题路径；
- 表格所属章节；
- 原始文档和章节来源。

例如：

```text
文档：车型配置指南
└─ 3. 库区配置
   └─ 3.2 库区模板
      └─ 3.2.1 修改宽度
```

检索命中“修改宽度”时，系统不仅获得局部内容，还能知道它属于“车型配置指南—库区配置—库区模板”，从而减少对象理解错误，并提供准确来源。

#### 4. 检索、评测与产品集成

- 检索链路不可拆解，无法定位问题发生在解析、召回、排序还是生成；
- 缺少独立测试集和统一评测指标；
- 检索策略难以针对内部术语和版本信息持续优化；
- 钉钉问答能力无法作为独立服务接入公司自有产品。

#### 5. 产品判断

因此，自建 RAG 不只是“换一个检索工具”，而是要重新建立完整的产品链路：

```text
问题理解与补充
→ 钉钉文档清洗
→ 保留目录结构的知识处理
→ 可控检索与生成
→ 来源引用与无答案处理
→ 独立评测
→ 对外提供问答服务
```

这套独立能力既用于解决现有知识覆盖、问题理解和检索质量问题，也为后续接入公司自有产品提供统一的知识问答服务。

## T｜Task

### 1. 项目目标

建设独立、可评测、可集成的企业 RAG 知识问答能力，解决工程知识在问题理解、文档解析、知识接入、检索效果和来源追溯上的问题。

首期目标不是直接替换所有人工咨询，而是验证以下闭环：

```text
工程人员自然语言提问
→ 补充必要上下文并改写问题
→ FAQ 或 RAG 检索
→ 返回带来源的答案
→ 无充分知识时拒答
→ 记录问题并推动知识补充
```

### 2. 我的职责

- 分析历史问答和 Bad Case，定义目标用户、核心场景和 MVP 范围；
- 设计问题补充、FAQ/RAG 分流、来源引用和无答案处理等产品规则；
- 制定文档治理、目录保留、外链处理和知识权限要求；
- 基于 Dify 搭建 RAG PoC，验证产品流程和问答链路可行性；
- 建立 Golden Set、验收指标和 Bad Case 迭代机制；
- 推动算法和研发完成定制化 RAG 建设、验收及上线运营。

### 3. 研发职责

- 设计并实现正式 RAG 系统架构；
- 完成文档解析、索引、检索、重排和生成服务；
- 选择模型、数据库及具体算法参数；
- 实现接口、权限、部署、监控、性能和稳定性；
- 根据测试集和 Bad Case 配合完成技术优化。

### 4. 共同职责

- 评审技术方案和系统边界；
- 确定质量、延迟和成本之间的取舍；
- 根据评测结果决定最终检索方案；
- 确定灰度条件和上线标准。

### 5. MVP 范围

#### 首期用户

- 国内外工程人员；
- 通过访客机制访问的外包人员。

#### 首期知识

- 研发共享知识库中的文本和表格；
- 有权限访问的一层钉钉内部链接；
- 保留文档标题、目录路径和原始来源。

#### 首期产品能力

- 问题完整性判断；
- 必要上下文追问与问题改写；
- FAQ 直答与 RAG 检索生成；
- 带来源回答；
- 无答案拒答；
- 问答记录及 Bad Case 分析。

#### 首期不做

- 不连接车辆实时状态；
- 不读取现场日志；
- 不执行终端命令；
- 不修改车辆配置；
- 不处理图片问答；
- 不在首期完成与公司自有产品的正式界面集成。

### 6. 成功标准

- 四类核心场景能够通过统一问答入口处理；
- 用户问题存在歧义时能够补充上下文，而不是直接猜测；
- 文本、表格、目录层级和可访问链接能够正确进入知识库；
- 回答提供可核验来源；
- 材料不足时能够拒答或提示补充；
- 可以通过独立测试集定位数据、检索和回答问题；
- 形成可供后续自有产品调用的独立问答服务。

## A｜Action

> 行动部分按需求分析、方案设计、知识治理、评测迭代和上线运营组织，不按技术组件简单罗列。

### A1：需求分析与方向验证

#### 分析输入

- 分析“小迦”2025 年 Q4 的 1,381 次问答、918 次访客来源和 21 个无回答问题；
- 结合问题歧义、表格解析、外链接入和文档召回等典型 Bad Case 定位问题。

#### 问题归因

- 输入：问题缺少车型、版本、模块或具体对象；
- 数据：外链知识无法接入，表格和目录结构解析不完整；
- 检索：自然语言与内部术语不一致，正确资料未召回；
- 平台：链路不可独立评测，也难以接入公司自有产品。

#### 产品判断

问题不能只靠补充 FAQ 或调整 Prompt 解决，需要建设包含问题改写、文档治理、可控检索、来源引用和无答案处理的独立 RAG 链路。

#### PoC 验证

基于 Dify 搭建 RAG PoC，验证文档接入、自然语言检索、带来源回答和无答案拒答的可行性，并据此确定定制化 RAG 方向及首期验收目标。

### A2：产品方案与 MVP 定义

#### 产品定位

将“小迦”规划为面向国内外工程及外包人员的独立、只读知识问答服务，首期解决四类工程知识查询，不替代现场诊断或人工决策。

#### 分层问答策略

- FAQ 直答：处理高频、稳定、有标准答案的问题；
- RAG 问答：处理需要检索文档、结合上下文或综合多份资料的问题；
- 补充问答：问题缺少车型、版本、模块或具体对象时，先追问再改写；
- 拒答：资料不足、来源冲突或超出权限时，明确说明原因，不猜测答案。

#### 核心问答流程

```text
用户提问
→ 判断问题是否完整
→ 必要时补充上下文并改写
→ FAQ 匹配
→ 未命中则进入 RAG 检索
→ 判断证据是否充分
→ 返回带来源答案或拒答
```

#### MVP 边界

- 首期处理文本、表格和有权限访问的一层内部链接；
- 回答必须展示原始文档及章节来源；
- 不连接车辆、不读取日志、不执行命令、不修改配置；
- 首期验证独立问答服务，后续再接入公司自有产品。

### A3：知识治理与问答链路建设

#### 知识范围

聚焦海外及工程团队使用的研发共享知识库，首期治理 1,000+ 篇有效文档，以文本和表格为主，图片暂不进入问答链路。

#### 产品侧治理工作

- 制定文档结构化、有效性和 FAQ 维护标准；
- 按知识域划分所属部门和内容负责人；
- 根据高频问题、无回答问题和 Bad Case 形成 FAQ 补充清单；
- 协调各部门完成所属知识的补充、纠错和审核；
- 跟进治理进度，并对文档完整性、来源和检索结果进行抽检验收。

#### 各部门内容职责

- 确认所属知识的业务正确性、适用车型和版本；
- 补充和审核本领域 FAQ 标准答案；
- 修正过期、错误或缺少上下文的内容；
- 确认文档权限、维护人和更新状态。

#### 研发技术职责

- 实现文档同步、自动清洗、去重和异常检测；
- 保留标题、目录路径、表格、代码、链接和来源元数据；
- 完成文档切分、索引、检索和失败重试；
- 提供处理失败清单和质量数据，配合产品完成验收。

#### 有效文档标准

- 正文可正常解析，非空、非重复；
- 具有明确标题、所属模块和原始来源；
- 保留目录层级、章节路径、表格和链接信息；
- 清洗后能够正常切分、建立索引并参与检索；
- 业务内容由所属部门完成审核。

#### FAQ 维护标准

每条 FAQ 至少包含标准问题、常见问法、标准答案、适用车型或版本、来源文档、维护部门和更新时间。产品负责清单、格式、优先级及进度，各部门负责答案内容和专业审核。

#### 知识时效管理

MVP 先完成基础控制：

- 入库前由所属部门确认内容可用；
- 保存知识来源、所属部门、更新时间、适用车型和软件版本；
- 回答展示来源及适用条件；
- 多份资料冲突或适用条件不明确时提示用户核验，不直接输出确定结论；
- 用户反馈知识过期后，进入人工更新和重新索引流程。

下一期再建设主动治理能力，包括有效期或复核周期、到期提醒、源文档变更检测、增量同步、冲突识别和按车型及版本过滤知识。旧文档不按日期直接删除，仍适用于旧车型或旧版本的内容继续保留。

#### 外部链接处理

外部链接分为“当前文档包含链接”和“答案存在于链接目标”两种情况：

1. 当前文档包含外部链接时，正文仍应正常清洗、切分和入库，链接本身不得阻断整篇文档进入知识库；
2. 保留链接文字、URL 和所在章节，将链接记录为文档元数据；
3. 对有权限访问的钉钉内部链接目标，作为独立文档进行清洗和索引，并保存入口文档与目标文档的引用关系；
4. 回答使用目标文档内容时，引用真正提供证据的目标文档；
5. MVP 最多跟随一层内部链接，不递归抓取全部关联页面；
6. 无权限、失效或暂不支持的链接保留地址并标记状态，公网网页首期不自动纳入知识库；
7. 链接目标内容继续遵循原始知识权限，不因进入 RAG 链路而扩大用户访问范围。

#### 链路建设

推动研发打通知识同步、清洗、切分、索引和检索全链路。产品侧负责数据范围、质量标准、来源追溯和异常处理要求，研发负责解析、存储、索引及具体技术实现。

### A4：评测、Bad Case 与方案迭代

#### 评测体系

- 围绕四类核心场景构建 52 道高频真实问题的 Golden Set；
- 定义 Recall@5、Hit@5、答案依据、来源支撑和无答案处理等指标；
- 使用同一问题集和知识版本对 Baseline 与 Candidate 进行对照测试。

#### Bad Case 推动检索优化

逐题对比标准证据、Hybrid 召回 Top 20 和最终 Top 5，将 Bad Case 区分为知识缺失、解析失败、召回失败、排序失败和生成错误；发现部分正确证据已进入候选集但未进入 Top 5，据此推动在 RRF 融合后增加 Cross-Encoder 重排。

历史问题集对照测试中，Recall@5由63%提升至87%，Hit@5由77%提升至88%，据此确定重排方案。该历史实验与52道新版Golden Set的证据边界单独记录在《05-简历数据说明》中。

- 推动研发完成问题补充、FAQ/RAG 分流、来源引用和无答案处理能力；
- 确认内部工程人员和外包访客的访问方式及权限范围。

#### 验收与发布

- 组织核心场景验收，检查答案、来源、拒答和权限是否符合产品规则；

```text

```
