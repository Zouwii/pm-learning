# 研发知识库 RAG 问答

## 一句话

面向研发新员工和跨模块协作人员的内部知识助手：围绕约 55G 原始图文知识资产，对研发项目、任务方案、项目节点、验收资料和模块文档进行结构化清洗与检索，通过 Hybrid RAG 和带引用问答降低跨空间查找与理解成本。

## 项目范围

- 原始知识资产约 55G；
- 已盘点 5,427 份 Markdown 和 19,886 张图片；
- 首期以 Markdown 文本与表格为主，图片保留原文回链；
- 只解决研发知识检索与问答，不包含工时、绩效、任务管理和其他管理功能；
- 不把全量多模态作为首期目标，是否投入 OCR 或视觉模型由 Bad Case 决定。

## 用户问题

研发资料分散在多个钉钉知识空间、项目文档和模块说明中。用户通常不是缺少某一篇文档的链接，而是不知道：

- 某个项目或模块有哪些历史方案；
- 某项任务的背景、负责人和相关资料在哪里；
- 项目节点、验收结论和版本信息记录在哪份文档中；
- 自然语言描述与文档术语不一致时，怎样找到真正相关的内容。

原生关键词搜索要求用户知道准确词汇，也难以把多份资料组织成带来源的直接回答。

### 小迦的历史能力缺口

- 包含外部链接的文档无法存入小迦知识库，相关资料因此不能进入后续检索和问答链路。
- 这会造成知识覆盖缺口：即使源文档真实存在，用户提问时系统仍可能因为知识库中没有该文档而无法回答。
- 该问题属于数据接入与知识覆盖问题，不应仅通过调整 Prompt、召回或重排解决。

| 渠道 | 问答次数 | 提问人数 | 提问人来源 | 答案不符-待更新 | 记录占比 |
| --- | ---: | ---: | --- | ---: | ---: |
| 群助理（智能问答功能） | 903 | 72 | 未记录 | 81 | 9%（按次数计算为 8.97%） |
| 小迦（AI 助理） | 1,381 | 未记录 | 访客 918（66%） | 21 | 2%（按次数计算为 1.52%） |

### 2026 年 Q2

| 渠道 | 问答次数 | 提问人数 | 答案不符 | 补充口径 |
| --- | ---: | ---: | ---: | --- |
| 群助理 | 768 | 70 | 55，记录占比约 7%（按次数计算为 7.16%） | 平均约 10.97 次/人 |
| 小迦钉钉助手 | 1,531 | 79 | 未统计 | 平均约 19.38 次/人 |

- 两个渠道共记录 2,299 次问答；由于用户可能重叠，不能将 70 人和 79 人直接相加为独立用户数。
- 群助理的“答案不符”是历史记录口径，尚不清楚来自全量人工审核、用户反馈还是其他统计方式，因此不能直接反推为 92.84% 的回答准确率。
- 小迦只有使用量数据，没有答案不符、准确率或满意度统计，不能用群助理的 7% 代替。

### 可确认的季度变化

- 总问答次数基本稳定：2025 Q4 为 2,284 次，2026 Q2 为 2,299 次，增加 15 次（约 0.66%）。
- 群助理问答次数从 903 降至 768，下降约 14.95%；提问人数从 72 降至 70。
- 群助理记录的答案不符占比从 9% 降至约 7%，下降约 2 个百分点，但统计方式是否完全一致仍需确认。
- 小迦问答次数从 1,381 增至 1,531，增长约 10.86%；由于 2025 Q4 缺少提问人数、2026 Q2 缺少答案不符统计，其他质量和用户变化不能直接比较。
- 2025 Q4 的“访客 918（66%）”保留为原始来源字段，不把 918 解释成独立提问人数。

### 自主 RAG 用量口径

自主 RAG 计划承接原群助理与小迦两个入口的知识问答需求。按两个历史季度的合计问答量估算，季度用量约为 **2,300 次问答**：2025 Q4 为 2,284 次，2026 Q2 为 2,299 次，季度均值约 2,292 次。

> 这是根据两个原入口合并得到的迁移承接量估算，不是自主 RAG 上线后由独立埋点统计出的实际调用量；两个入口的提问人数可能重叠，因此不估算独立用户数。

## 产品方案

```text
Markdown / 表格 / 仓库设计文档
        ↓
清洗、结构保真、版本与来源元数据
        ↓
基于标题层级的 parent-child chunking
        ↓
FULLTEXT / FTS + bge 向量检索
        ↓
RRF 融合 + Cross-Encoder reranker
        ↓
上下文扩展、去重与权限过滤
        ↓
带来源引用的 LLM 回答 / 信息不足时拒答
```

## 我的核心工作

1. 将宽泛的“全公司知识问答”收敛为研发项目与模块知识场景，明确首期用户、问题类型和数据白名单；
2. 对约 55G 原始图文资产进行数据盘点，首期优先处理 5,427 份 Markdown，图片保留回链；
3. 设计并实现 Markdown 清洗、标题层级恢复、表格保真和 parent-child chunking；
4. 建立文档来源、标题路径、更新时间、workspace、node 和内容版本等可追溯元数据；
5. 搭建全文与向量双路召回、RRF 融合、Cross-Encoder 重排和带引用问答链路；
6. 设计真实问题集和 baseline/candidate 实验，按解析、检索、回答和性能四层评估；
7. 通过 Bad Case 判断问题属于数据缺失、清洗、切分、召回、排序还是生成，并据此决定迭代优先级。

## 评测框架

| 层级 | 核心指标 |
| --- | --- |
| 数据与解析 | 文档成功率、正文保留率、表格完整率、空文档与重复文档比例 |
| 检索 | Recall@5、MRR、nDCG@5 |
| 回答 | 引用正确率、事实一致率、拒答准确率 |
| 产品与性能 | 端到端延迟、问题完成率、来源点击与用户反馈 |

V2 实验必须在冻结的同一语料和独立真实问题集上比较 baseline 与 candidate，结果产出后再填入项目描述和 resume。

## 历史检索实验：v4 精简答案口径复评

> 数据来源：v1 的 26 道独立问题分别完成无重排和有重排两组测试，共形成 **52 条离线评测记录**。v4 不是新的检索模型，而是将评价标准调整为“每题最多要求召回 2 个核心证据 chunk”后，对同一批结果重新计分。下表不是当前 leaf 化 V2 的实验结果。

| 指标 | 无 reranker：Hybrid RRF | 有 reranker：Hybrid RRF Top 20 + bge-reranker-base | 变化 |
| --- | ---: | ---: | ---: |
| Recall@5（逐题宏平均） | 63.46% | **86.54%** | +23.08 个百分点 |
| Recall@5（整体核心证据） | 63.04%（29/46） | **86.96%（40/46）** | +23.92 个百分点 |
| 完整召回率 | 50.00%（13/26） | **84.62%（22/26）** | +34.62 个百分点 |
| 问题命中率 Hit@5 | 76.92%（20/26） | **88.46%（23/26）** | +11.54 个百分点 |
| MRR | 55.90% | **69.68%** | +13.78 个百分点 |
| nDCG@5（最多 2 个证据） | 52.12% | **72.45%** | +20.33 个百分点 |

**历史选型结论**：加入 reranker 后，核心证据 Recall@5 从约 63% 提升到约 87%，问题命中率接近 90%。最终选择 `bge-reranker-base`，而不是效果略高但约 2.2 GB 的 `bge-reranker-v2-m3`；历史服务器记录约为 1 秒/题，兼顾效果、延迟和模型体积。

**口径边界**：这组结果可用于讲述 v1 的检索优化和选型，但不能描述成 v2 leaf 链路的效果，也不能把离线 Hit@5 等同于回答准确率或用户满意度。
