# Diagnosis-Agent：MVP 范围与产品落地

> 本文档说明项目为什么选择“错误码诊断＋高频故障诊断”作为 MVP，以及 Workflow 与 Agent 如何协同。技术框架不是项目讲述主线。

## 1. MVP 结论

首期不做通用故障诊断，而是聚焦两类具有重复性和标准排查路径的问题：

1. **错误码诊断**：已有明确错误码，需要结合版本、日志和上下游状态，从“报错模块”继续排查到“根因模块”。
2. **高频故障诊断**：只有问题现象，没有能够直接定位的错误码，但存在可复用的分步排查 SOP。

历史问题复盘中，196 个导航相关问题里有 36 个错误码类 Bug 和 53 个高频问题，合计 89 个，约占 45%。因此先处理覆盖率较高、排查路径相对稳定的问题，再根据 Bad Case 扩展能力。

## 2. 产品目标与边界

### 产品目标

- 帮助应用工程师快速理解问题并选择诊断路径；
- 把资深工程师的排查经验转换为标准、可执行的流程；
- 用日志、ROS Bag、配置和错误码等证据支撑诊断结论；
- 尽可能将问题收敛至单一责任模块，或产出可继续排查的交接材料。

### 产品边界

- Agent 不替代研发完成代码级根因定位和 Bug 修复；
- 没有命中错误码知识或高频 Workflow 的问题不强行自动诊断；
- 材料不足、证据冲突或必须现场操作时，转由应用工程师或领域研发处理；
- 默认只读，未经人工确认不执行重启、改参数、升级等高风险操作。

## 3. Workflow 与 Agent 的分工

| 能力 | 主要职责 | 设计原因 |
| --- | --- | --- |
| Agent | 理解问题描述、提取错误码和上下文、选择诊断路径、组织证据并生成可读结论 | 输入表达不统一，需要语义理解和动态路由 |
| Workflow | 按既定顺序调用日志、Bag、配置等工具，执行检查项和条件分支 | 故障排查需要稳定、可复现、可验证 |
| 人工 | 补充材料、复核证据和结论、处理超出范围的问题 | 控制错误归因和现场操作风险 |

核心原则是：**Agent 负责理解和决策，Workflow 负责执行和留证，人工负责最终复核与兜底。**

## 4. 两条诊断路径

### 4.1 错误码诊断

1. 从问题描述和诊断材料中提取错误码；
2. 匹配适用版本和对应的错误码知识；
3. 检查直接触发条件、上游依赖和相应日志证据；
4. 区分“抛出错误的模块”和“导致错误的模块”；
5. 输出根因方向、关键证据、已排除方向和下一步建议。

### 4.2 高频故障诊断

1. 识别问题现象和当前任务阶段；
2. 匹配对应的高频故障 Workflow；
3. 按流程依次检查场景、配置、日志和上下游模块；
4. 每一步记录正常或异常判据，并决定下一步分支；
5. 能收敛时输出唯一模块，不能收敛时输出候选方向和已排除项。

## 5. 知识如何转化为产品能力

### 错误码知识标准

每篇错误码文档至少包含：

- 错误码、问题现象及适用版本；
- 代码抛错位置与直接触发条件；
- 可能的上游原因和责任模块；
- 所需日志、配置或 Bag 证据；
- 检查步骤、正常/异常判据及下一步动作。

### 高频故障 Workflow 标准

每套 Workflow 需要明确：

- 适用与不适用条件；
- 执行前必须具备的材料；
- 每个检查项的输入、工具、判断标准和证据；
- 不同结果对应的下一步分支；
- 停止、转人工条件与可能归属模块。

项目协同业务和研发沉淀了 150 篇错误码排查文档和 10 套高频诊断流程。模型可以辅助生成初稿，但错误触发条件、上下游依赖和判断标准必须由领域研发审核。

## 6. 端到端产品流程

提交 Teambition 问题单
→ 读取问题描述和附件
→ 检查时间、版本及诊断材料是否完整
→ Agent 识别错误码或高频故障场景
→ 匹配错误码知识或高频 Workflow
→ 调用既有诊断工具逐步执行
→ 记录每步判据和原始证据
→ 输出收敛结果或转人工建议
→ 应用工程师复核并完成交接

## 7. 验收与灰度

### 评测方法

- 从首期目标场景中定向筛选 50 个真实历史 Case；
- 以应用工程师复核的最终归属模块为标准答案；
- 分别记录已收敛、范围缩小和转人工，不把“输出了模块名”直接视为成功；
- 对未收敛和判断错误 Case 分层归因，再补充知识、修改 Workflow 或收紧边界。

### 灰度结果

- 50 个目标 Case 中，40 个收敛至唯一责任模块，收敛率为 80%；
- 40 个已收敛 Case 中，37 个判断正确，准确率为 92.5%，简历中概括为 92%；
- 典型软件故障的初筛与模块转交时间由约 60 分钟缩短至约 10 分钟，对应降低 80%+；
- “季度节省约 95 小时”是根据灰度样本和种子用户问题量外推的测算值，不是系统埋点累计值。

详细口径见 [04-测试集数据说明.md](04-测试集数据说明.md)。

## 8. Bad Case 带来的产品迭代

| Bad Case | 问题本质 | 产品迭代 |
| --- | --- | --- |
| 材料不足 | 缺少时间、版本或关键日志 | 增加完整性检查和定向补充提示 |
| 未命中流程 | 不属于已沉淀的错误码或高频场景 | 明确降级为人工排查，避免自由推理 |
| 过程不可见 | 用户无法判断当前执行步骤 | 展示步骤、进度、异常状态和重试入口 |
| 证据定位不清 | 结论与原始日志之间缺少关联 | 展示证据来源、时间窗及支持/排除关系 |
| 跨模块归因错误 | 将报错模块或相关异常当成根因 | 补充上下游检查；证据不足时不输出唯一模块 |

## 10. 面试口述版

这个项目的 MVP 没有定义成通用故障诊断，而是基于历史问题复盘，先聚焦错误码和高频故障两类具有稳定排查路径的问题。

产品上采用 Workflow 与 Agent 协同：Agent 负责理解问题、提取上下文和选择路径，Workflow 负责按标准步骤调用日志、Bag 和配置检查能力，每一步都留下可核验证据。证据不足或没有匹配到标准流程时，系统会明确转人工，而不是让模型猜根因。

我主要负责首期范围、双路径方案、知识标准、人工接管和验收体系，并协同业务与研发沉淀 150 篇错误码文档和 10 套高频诊断流程。灰度阶段用 50 个真实 Case 验证，模块归属收敛率为 80%，已收敛 Case 的判断准确率为 92.5%。
