# Diagnosis-Agent：从 Claude MVP 到 LangGraph 一期

## 1. 路线结论

项目采用两阶段路线：

1. 先用 Claude + Skill + ttyd 做 MVP，低成本验证已有诊断能力在真实支持场景中的可用性；
2. 再用 LangGraph 将已经验证的能力结构化，补齐 Case 状态、流程控制、审计、安全和评估能力。

LangGraph 的价值不是替代 Claude 的推理能力，而是将对话式 Agent 产品化。

## 2. MVP：Claude + Skill + ttyd

### 要验证的假设

- 技术支持是否愿意用自然语言发起诊断；
- 已有 orchestrator 和 Skills 能否覆盖真实 Case；
- 四类来源还缺少哪些数据工具和领域能力；
- AI 输出能否帮助初步定位或提高转交研发的材料质量。

### 产品与技术分工

ZHR 设计场景入口、参数输入、会话和结果交互。开发同事采用 ttyd 作为 Web 终端承载层，将 Claude Code 及其 Skill 运行环境接入管理平台。算法同事继续维护 orchestrator、Skill 规范和领域能力。

这一实现可以较完整地复用 Claude 已有的 Agent Loop、上下文推理和工具调用能力，适合快速验证，但不等同于成熟的 Case 工作流产品。

### MVP 的产品价值

- 减少用户本地安装和配置 Claude 环境的成本；
- 最大程度复用既有 orchestrator 和 Skills；
- 用真实 Case 暴露数据、工具和交互缺口；
- 为后续结构化建设提供基线行为。

## 3. MVP 暴露的产品化问题

- 诊断状态主要存在于对话中，不易形成统一 Case；
- 工具调用、路由理由和中间证据不便统计与审计；
- 同类问题的执行步骤和输出结构可能不完全一致；
- 中断恢复、失败重试和人工接管能力不足；
- 安全边界较依赖 Prompt 与 Skill 自身约束；
- 无法稳定判断失败来自采集、分析、外部证据还是报告环节；
- 难以对不同版本做可重复的一致性评测。

## 4. LangGraph 一期产品目标

一期主题定义为：**诊断流程结构化与可控化**。

一期不追求重写全部 Claude 推理，也不建设多个 Agent 自由协作。它需要完成三件事：

1. 建立原 orchestrator 的兼容基线；
2. 将完整流程拆成可观察、可测试、可恢复的节点；
3. 为后续独立工作流准备统一的 Case、证据和安全契约。

## 5. 三版本定位

| 版本 | 流程 | 产品定位 | 当前事实边界 |
| --- | --- | --- | --- |
| `origin-v1` | `START → diagnosis_cli → END` | 一次性调用迁移后的完整 `diagnosis_cli`，复刻原 orchestrator，作为兼容基线 | 入口已迁移，完整行为仍需真实 Case 验收 |
| `origin-split` | `START → collect → analyze → report → END` | 使用拆分后的同一套模块完成等价流程，获得节点级可测试性 | 节点已建立，完整闭环和等价性仍需验证 |
| `graph-v1` | 独立演进 | 在兼容版本稳定后增加路线控制、证据汇合、预算、恢复和人工接管 | 后续演进项，不能说成已经完整上线 |

`origin-v1` 不是把 Skill 文本复制进 Prompt，也不是用一次普通模型调用模拟诊断；它必须调用完整 `diagnosis_cli`，覆盖采集、分析、专项路由、外部证据和报告生成。

`origin-split` 可以改变工程结构，但不能减少原流程行为。拆分的目的首先是可观察和可测试，不是改变诊断结果。

## 6. 一期功能范围

### Case 标准化

每次诊断创建独立 Case，统一记录：

- 来源类型与用户现象；
- 原始材料和采集结果；
- 当前执行节点与状态；
- 错误码、问题类型和中间发现；
- 工具调用与错误记录；
- 证据引用、结论状态和报告；
- 待用户补充或待人工确认的事项。

### 四路采集

固定支持 `tb_task`、`internal_robot`、`remote_site`、`local_logs`。客户端不能传入任意 Skill 名称；服务端通过白名单将场景映射到允许的采集器和参数规则。

### 流程拆分

- `collect`：按来源采集并归档材料；
- `analyze`：执行材料扫描、错误码提取、时间窗分析、规则和 Playbook；
- `report`：汇总证据与结论状态，生成结构化报告；
- 后续 `graph-v1` 再增加固定路线选择、证据汇合和人工决策节点。

### 状态与进度

通过 Case API 和 SSE 向前端展示创建、采集、分析、生成报告、等待补充、失败和完成等状态。流程状态从终端对话中独立出来，为恢复和人工接管提供基础。

### 结论约束

报告使用 `confirmed`、`likely`、`need_human`、`insufficient_data` 等状态区分证据充分度。材料不足时明确输出缺失项，不用模型猜测根因。

### 安全边界

- 一个 Case 只使用一种主要采集来源；
- 默认只读，不自动重启、改配置或发版；
- 远程写入和现场风险操作必须进入人工确认；
- 本地日志只能读取允许的工作区或租户目录；
- 工具名称、参数和路线由服务端白名单控制；
- 工具调用保留输入摘要、结果位置、耗时和错误类别，不记录凭据；
- Case 按用户和租户隔离。

## 7. 一期验收设计

### 兼容性

- `origin-v1` 是否完整执行原 `diagnosis_cli`；
- 四类来源是否都覆盖采集、分析、专项路由、外部证据和报告；
- 是否出现用简单 Prompt 代替完整 orchestrator 的行为退化。

### 一致性

使用相同真实 Case 对比 `origin-v1` 与 `origin-split`：

- 输入材料是否一致；
- 错误码和问题类型是否一致；
- 关键证据是否遗漏；
- 结论状态与根因方向是否一致；
- 建议动作是否存在实质冲突；
- 材料不足时是否都能正确转人工。

一致性不是要求报告文字逐字相同，而是要求关键事实、证据、结论方向和安全行为等价。

### 可控性

- 越权路径和任意 Skill 调用是否被拦截；
- 失败是否能定位到具体节点；
- 缺材料、权限失败和风险动作是否产生明确人工交接；
- 执行记录是否支持回看和复盘。

### 真实 Case 可用性

由技术支持评价：材料是否完整、证据是否可核验、建议是否可执行、是否减少重复补问。没有真实数据前不对外宣称准确率或效率提升数字。

## 8. 一期明确不做

- 不完全替换 Claude 或既有领域 Skills；
- 不让多个 LLM Agent 无限制自由协作；
- 不允许模型生成任意 shell、URL 或工具名称；
- 不自动执行现场写操作；
- 不在兼容性尚未验证前删除 ttyd/origin 基线；
- 不把设计中的 `graph-v1` 能力表述成已全量上线。

## 9. 面试讲述版本

我在项目中主要负责产品方案。首先，我把机器人诊断需求梳理成 Teambition 任务、公司内网机器人、客户远程现场和本地日志四类入口。算法同事已经具备部分 orchestrator 和标准化 Skills，我发现完整链路还缺少 Teambition 类型的 Skill，因此提出了任务、活动记录和附件读取能力需求。

在交互上，我设计了场景选择、诊断输入、AI 会话和结果查看流程。为了尽快验证已有诊断能力是否能解决真实问题，我们没有一开始就建设复杂工作流，而是由开发同事通过 ttyd 将 Claude Code 和 Skill 运行环境接入平台。这个 MVP 最大程度复用了 Claude 的 Agent Loop，也降低了用户配置环境的成本。

真实 Case 验证过程中，我们发现终端对话适合验证能力，但在 Case 状态、过程追踪、失败恢复、安全审计和效果评估上不够产品化。因此后续规划 LangGraph 一期：保留 `origin-v1` 一次性调用完整 orchestrator 作为兼容基线，同时建设 `origin-split`，把采集、分析和报告拆成可观察节点，并用同一批 Case 验证关键证据、结论方向和安全行为的一致性。在兼容基线稳定后，再通过 `graph-v1` 增加路线控制、证据汇合和人工接管。

我的主要贡献不是开发底层算法，而是定义四类场景、识别 Skill 缺口、设计交互、选择 MVP 验证路线，并根据真实使用问题定义从 Claude 原型到 LangGraph 产品化工作流的演进边界。
