# Diagnosis-Agent：50 Case 测试记录

> 本文档用于逐项记录 50 个测试 Case 的评测口径与结论。仅保留已经讨论确认的数据，不再反推或虚构逐条 Case 明细。

## 1. 测试集来源与筛选口径

通过分析 Q2 历史 TB 问题单，识别出约 45% 的问题属于首期可覆盖的错误码、软件 Bug 及高频问题场景。在这些目标场景中筛选 50 个真实历史 Case 构建专项评测集，用于验证 Agent 的诊断效果。

因此，50 个测试 Case 并非从全量问题中随机抽取，而是从首期可处理场景中定向筛选：

- 全量 TB 问题单中，约 45% 属于首期目标场景；
- 50 个测试 Case 全部属于首期模板可处理范围；
- 评测结果反映 Agent 在目标场景内的表现，不能直接代表全部 TB 问题的效果。

评测漏斗为：

`全量 TB 问题单 → 约 45% 首期目标场景 → 筛选 50 个目标 Case 开展专项评测`

## 2. 模块归属收敛率

50 个目标 Case 均能依据错误码或高频问题 SOP 完成必要检查，并至少排除一类候选原因，问题原因范围缩小率为 100%。其中 40 个最终收敛至单一责任模块：

`模块归属收敛率 = 40 / 50 = 80%`

其余 10 个 Case 虽然未收敛至唯一模块，但均能排除部分原因并形成后续人工排查建议。

### 2.1 收敛标准

“收敛”不能只看 Agent 是否输出了一个模块名称，而应同时满足以下条件：

1. 完成对应错误码或高频问题 Workflow 的关键检查步骤；
2. 最终指向唯一责任模块，而不是给出多个候选模块；
3. 结论具有日志、ROS Bag、配置参数或错误码等证据支持；
4. 能够输出明确的模块归属及证据化交接材料。

模块判断是否正确不属于收敛标准，应通过“已收敛 Case 判断准确率”单独衡量。Agent 即使收敛至单一模块，也可能出现模块判断错误。

### 2.2 结论状态

| 结论状态 | 定义 |
| --- | --- |
| 已收敛 | 完成关键检查，输出唯一责任模块及相应证据 |
| 范围缩小 | 已排除部分模块，但仍存在两个及以上候选模块 |
| 转人工 | 已完成 SOP 范围内的检查，但剩余方向需要人工操作或领域专家确认 |

### 2.3 未收敛原因

10 个未收敛 Case 的原因如下：

| 未收敛原因 | Case 数 | 具体表现 |
| --- | ---: | --- |
| 跨模块证据耦合 | 4 | 导航、地图、调度或本体均存在关联表现，能够排除部分原因，但无法确认唯一责任模块 |
| 缺少正向归因证据 | 3 | SOP 能够证明若干链路正常，但剩余候选方向只有排除性证据，不能直接确认为根因模块 |
| SOP 诊断粒度不足 | 2 | 当前模板只能收敛至模块组合或问题方向，尚未细化到唯一责任模块 |
| 证据存在冲突 | 1 | 日志、ROS Bag 或配置数据指向不同方向，需要领域专家进一步判断 |
| **合计** | **10** | — |

其中：

- 10 个 Case 均能完成 SOP 范围内的检查并缩小问题范围；
- 由于缺少能够支持唯一归属的充分证据，最终输出候选方向及证据化人工交接材料。

## 3. 已收敛 Case 判断准确率

40 个已收敛 Case 中，37 个模块归属判断与应用工程师最终确认结果一致，3 个判断错误：

`已收敛 Case 判断准确率 = 37 / 40 = 92.5%`

该指标只以已经收敛至单一责任模块的 40 个 Case 为分母，不包含 10 个未收敛 Case。

判断正确的标准为：Agent 输出的唯一责任模块与应用工程师复核后确认的最终归属模块一致。证据展示完整但模块归属错误，仍计为判断错误。

### 3.1 三个错误 Case 的情况

| 错误类型 | Case 数 | 具体情况 |
| --- | ---: | --- |
| 将报错模块误判为根因模块 | 1 | 错误码由导航模块抛出，但最终根因来自上游地图或任务参数，Agent 将报错来源直接判断为责任模块 |
| 跨模块参数归因错误 | 1 | Agent 已检查地图、调度和导航参数，但对异常参数的责任边界判断错误，将上游输入问题归属到下游执行模块 |
| 相关性证据被误判为因果证据 | 1 | 日志时间窗内存在明显异常事件，但该事件并非真正根因，Agent 据此收敛到了错误模块 |
| **合计** | **3** | — |

三个错误 Case 均完成了 SOP 检查并提供了可核验证据，问题不在于没有执行排查，而在于跨模块场景中对证据与最终责任模块的归因判断错误。

需要区分以下两个指标：

| 指标 | 计算方式 | 结果 | 衡量内容 |
| --- | --- | ---: | --- |
| 模块归属收敛率 | 40 / 50 | 80% | Agent 能否将问题收敛至唯一模块 |
| 已收敛 Case 判断准确率 | 37 / 40 | 92.5% | Agent 给出唯一模块后，判断是否正确 |

从全部测试集看，Agent 正确完成单一模块归属的比例为：

`全量正确定位率 = 37 / 50 = 74%`

## 4. Agent 运行时间

Agent 的完整运行链路为：

`提交 TB 任务链接 → 读取任务描述及活动记录 → 自动下载日志、ROS Bag 及附件 → 解压并裁剪问题时间窗 → 提取错误码和异常特征 → 执行 SOP 诊断项 → 汇总证据 → 生成结论项表`

50 个测试 Case 按材料规模和诊断复杂度分为三类：

| Case 类型 | Case 数 | 平均运行时间 | 主要耗时 |
| --- | ---: | ---: | --- |
| 错误码明确、附件较小 | 15 | 约 3 分钟 | 材料下载、错误码匹配及报告生成 |
| 标准日志及多项 SOP 检查 | 25 | 约 5 分钟 | 日志下载、时间窗裁剪及逐项诊断 |
| 包含较大 ROS Bag 或多附件 | 10 | 约 8 分钟 | 文件下载、解压、数据提取及多路径判断 |

加权平均运行时间为：

`(15 × 3 + 25 × 5 + 10 × 8) / 50 = 5 分钟`

因此：

`Agent 单 Case 平均运行时长约 5 分钟`

### 4.1 统计边界

- 起点：用户提交 TB 任务链接并启动诊断；
- 终点：系统生成完整的 SOP 结论项表及证据化报告；
- 包含：TB 材料读取、附件下载、日志与 ROS Bag 处理、SOP 执行、证据汇总和报告生成；
- 不包含：报告生成后应用工程师进行 ROS Bag 回放、现场复现或咨询领域研发的时间。

## 5. 使用前人工处理耗时估算

潘铮 Q2 共处理 196 个问题单，各类处理方式及标准耗时如下：

| 问题处理方式 | Q2 Case 数 | Q2 占比 | 单 Case 人工耗时 |
| --- | ---: | ---: | ---: |
| 直接转走 | 5 | 2.55% | 5 分钟 |
| 非自身问题原因排查 | 79 | 40.31% | 10 分钟 |
| 自身问题深入排查 | 97 | 49.49% | 60 分钟 |
| 远程现场处理 | 15 | 7.65% | 120 分钟 |
| **合计** | **196** | **100%** | — |

“直接转走”无需进入 Agent 诊断，“远程现场处理”包含现场操作且超出首期诊断 Agent 的任务边界，因此两类问题不进入 50 Case 测试集。测试集从“非自身问题原因排查”和“自身问题深入排查”两类问题中筛选。

两类有效问题的数量比例为：

`非自身问题原因排查 : 自身问题深入排查 = 79 : 97 ≈ 4 : 5`

按照该比例映射到 50 个测试 Case，并进行整数调整：

- 非自身问题原因排查：`50 × 79 / (79 + 97) ≈ 22` 个；
- 自身问题深入排查：`50 × 97 / (79 + 97) ≈ 28` 个。

| 问题处理方式 | Case 数 | 使用前单 Case 耗时 | Agent 辅助后单 Case 耗时 | 单 Case 节省 | 累计节省 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 非自身问题原因排查 | 22 | 10 分钟 | 5 分钟 | 5 分钟 | 110 分钟 |
| 自身问题深入排查 | 28 | 60 分钟 | 35 分钟 | 25 分钟 | 700 分钟 |
| **合计** | **50** | — | — | — | **810 分钟** |

自身问题深入排查的 Agent 辅助后耗时由两部分组成：Agent 自动完成材料下载、SOP 检查及结论生成约 5 分钟，应用工程师基于结论继续回放或专业判断约 30 分钟，总计约 35 分钟。

计算结果：

- 使用前人工处理总耗时：`1,900 分钟`，约 `31.7 小时`；
- 使用前平均单 Case 处理耗时：`1,900 / 50 = 38 分钟`；
- Agent 纯运行总耗时：`50 × 5 = 250 分钟`，约 `4.2 小时`；
- Agent 平均单 Case 运行时长：`5 分钟`；
- 50 个 Case 共减少人工处理时间：`22 × 5 + 28 × 25 = 810 分钟`，约 `13.5 小时`；
- 估算整体处理耗时下降：`810 / 1,900 = 42.6%`。

该结果基于潘铮 Q2 两类有效诊断问题的数量比例进行估算，用于评估潜在效率收益，不代表 50 个 Case 的逐单实测耗时。

## 6. 单人季度节省工时估算

假设下一季度单人问题量与潘铮 Q2 相当，仍为 196 单；其中约 45.4% 属于首期 Agent 可覆盖的错误码、软件 Bug 及高频问题场景：

`196 × 45.4% ≈ 89 个目标 Case`

按照非自身问题原因排查与自身问题深入排查约 4:5 的比例分配：

- 非自身问题原因排查：约 40 个，单 Case 节省 5 分钟；
- 自身问题深入排查：约 49 个，单 Case 节省 25 分钟。

预计单人季度节省工时为：

`40 × 5 + 49 × 25 = 1,425 分钟 ≈ 23.8 小时`

按每天 8 小时计算，相当于：

`23.8 / 8 ≈ 3 个工作日`

因此，在问题量、问题结构及 Agent 使用率保持一致的情况下，预计每名应用工程师每季度可减少约 24 小时问题排查工时。

## 7. 当前阶段结论

从首期可覆盖场景中筛选 50 个真实历史 Case 开展专项评测。全部 Case 均能依据错误码或高频问题 SOP 完成必要检查并缩小问题原因范围；其中 40 个收敛至单一责任模块，模块归属收敛率达到 80%，37 个模块归属判断正确，已收敛 Case 判断准确率为 92.5%；Agent 从读取 TB 任务、自动下载材料到生成证据化报告的单 Case 平均运行时长约 5 分钟。
