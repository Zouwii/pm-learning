# AGV 智能诊断产品：STAR 项目讲述底稿

> 这份底稿以产品经理视角讲述。技术实现只用于解释产品取舍，不作为项目主线。标记“待补”的内容不能在正式 interview 中当作确定事实。

## 一句话介绍

我主动发起并负责定义一款面向 AGV 应用工程师的诊断 Agent：由研发为高频问题和错误码问题提供标准排查流程，Agent 负责根据 Teambition 问题单和现场材料逐步执行、记录证据和提示补充信息，帮助应用工程师加快问题解决或向研发转交的速度。

---

## S：Situation，项目背景

2026 年 3 月，在公司寻找业务 AI 化机会的背景下，我结合现场项目复盘，主动提出建设 Diagnosis-Agent。

当时的问题处理链路是：现场工程师发现问题后提交 Teambition 任务，应用工程师接单后阅读问题描述和附件，再结合日志、错误码、研发文档和个人经验完成排查；能解决的直接给出处理方案，不能解决的再携带材料转交研发。

真实痛点首先是效率。现场问题从提单到得到有效处理的流转速度较慢，多数问题可能需要半天甚至一天才能处理完，有时还需要项目经理进行催促。时间不只消耗在判断根因上，也消耗在理解表述不清的问题、补齐材料、重复执行检查和多角色之间的往返沟通。

我进一步分析了导航应用工程师处理的 196 个问题，其中错误码类 Bug 有 36 个，五类高频问题有 53 个，合计 89 个，约占 45%。这意味着不必一开始覆盖所有长尾问题，可以先从高频问题和错误码问题中提取标准流程。

（访谈部分）我访谈了 4 名应用工程师和 2 名测试人员。
应用工程师帮助我还原现场问题从接单、日志分析到模块转交的实际过程；
测试人员则重点说明 Teambition 单据的提交和流转规则，以及哪些信息必备、哪些 Bag、图片或日志属于可选补充材料。
访谈进一步验证了，问题单的表述和材料完整度并不稳定，因此 Agent 不能对所有问题自由推理并直接给出结论。

错误码类 Bug 和高频问题存在相对稳定的排查路径，但这些知识需要由熟悉机理和代码的研发人员提供并审核，而不是让 Agent 自行生成。应用工程师借助 Agent 调用这些标准流程，可以减少反复查找和遗漏步骤，同时仍保留对结论的人工确认。

因此我将产品目标定义为：先把研发审核过的高频问题和错误码标准排查流程交给 Agent 执行，帮助应用工程师更快完成信息补齐、分步排查、问题解决或带证据转交。产品不试图替代应用工程师和研发，也不对表述不清、材料不足或长尾的问题强行给出结论。

“到点精度异常”是一个典型例子。它在 Q2 导航问题中属于高频提示，但看到这个提示并不能直接判断根因。应用工程师通常需要依次完成五步检查：

1. 确认点位属性和任务场景，是快速到点还是精确到点；
2. 根据三代机型和现场配置，确认实际生效的到点精度阈值；
3. 从同期导航日志中提取实际到点误差，与生效阈值进行比较；
4. 检查到点时间窗口内是否发生定位跳动；
5. 检查控制器结束时误差是否已经收敛。

这五步把一个模糊的“到点不准”现象，逐步收敛到场景或阈值不匹配、实际误差超限、定位不稳定、控制未收敛等可验证方向。

### S 口述版本

2026 年 3 月，在公司寻找业务 AI 化机会的背景下，我结合现场项目复盘，主动提出建设 Diagnosis-Agent。

现有链路是现场工程师先提 Teambition 单，应用工程师看单后再找日志、查错误码和研发文档完成排查。真实痛点是问题流转和排查效率慢，多数问题可能需要半天甚至一天，有时还需要项目经理催促。问题描述不清、材料不完整和排查步骤依赖个人经验，都会延长这个过程。

我分析了导航应用工程师处理的 196 个问题，错误码类 Bug 和五类高频问题合计 89 个，约占 45%。这些问题存在相对稳定的排查路径，适合优先标准化；但标准流程需要由研发根据机理和代码提供并审核，不能让 Agent 自己猜。

因此，我将产品定位为应用工程师的辅助诊断工具：研发负责提供标准排查流程，Agent 负责根据问题单和现场材料逐步执行并记录证据，应用工程师保留判断和确认权。它优先解决高频和错误码问题的处理效率，无法处理的问题再带着已有证据转交研发。

## T：Task，我的任务

我虽然正式岗位是软件开发工程师，但在这个项目中承担了发起人和 AI 产品负责人的角色。我的核心任务，是将研发的知识沉淀转化为 Agent 可执行的标准排查流程，并将它接入现场提单到应用排查的真实链路，以缩短高频和错误码问题的处理时间。

围绕这个目标，我主要负责三件事：

1. 界定高频问题和错误码问题的首期范围，明确哪些问题适合标准流程，哪些必须转人工；
2. 制定 Agent 可执行的知识标准，由领域研发提供和审核具体排查流程；
3. 设计从问题单输入、材料确认、流程执行到结果确认的产品链路，并通过真实 Case 验证是否缩短处理时间。

我的职责重点是场景定义、产品方案、知识标准和效果验收；算法同事负责 Agent 框架与工具执行，领域研发负责错误码知识编写和技术评审，开发同事负责正式系统接入。

## A：Action，我采取的行动

### A1. 收敛首期场景

我没有把产品定义成通用故障诊断，而是聚焦错误码和高频问题两类可标准化场景：错误码问题通常有明确触发条件和上下游检查项；高频问题虽然可能只有现象，但可以由研发拆成稳定的排查步骤。表述不清、材料不足、未命中标准流程或需要修改现场的 Case，必须请求补充信息或转人工。

### A2. 把专家经验转化为 Agent 可执行知识

我定义了统一的知识模板，要求每份流程写清适用版本、触发条件、所需材料、上下游依赖、检查步骤、正常与异常判据以及下一步动作。领域研发负责提供和审核具体技术内容；我负责把它变成 Agent 可调用、产品可展示、测试可验收的结构。每一步都必须产生可核验的证据；材料不足或证据冲突时，系统只能提示补充材料或转人工，不能强行判断。

### A3. 设计并推动产品落地

我将内网车辆、Teambition 任务、远程现场和本地文件设计为四类材料入口。对当前最典型的 Teambition 链路，用户提供任务链接或其他来源标识，系统先识别问题和材料来源，再让用户确认后创建 Case。用户不需要理解或选择底层 Skill。

进入诊断后，系统按标准流程完成材料检查、日志与 Bag 获取、错误码或特征识别和逐项排查，并展示当前步骤、排查结果、证据和执行记录。

我通过 Vibe Coding 完成前端初版，用可运行原型验证交互，并协同算法和开发同事推进 Agent、工具能力与正式系统实现。考虑到现场安全，产品默认只读，高风险操作必须由人工确认。

### A4. 定义真实 Case 验收方法

我从首期目标场景整理了 50 个 Case 作为候选测试集。验收不只看最终结论，还要检查入口识别是否正确、材料是否完整、标准流程路由是否正确、每个结果是否有可复核证据，以及从接单到解决或形成有效转交的处理时间。

50 个 Case 来自首期目标场景，不代表全量随机问题。当前还在开发和真实 Case 验证阶段，尚未形成可以对外宣称的提效或准确率结果。

## R：Result，项目结果

项目当前处于开发和真实 Case 验证阶段，还不能将结果表述为已上线的业务提效。

已完成的是：将产品范围收敛为高频和错误码问题；明确研发提供标准流程、Agent 执行并留存证据、应用工程师确认结果的人机分工；完成创建 Case 和诊断过程的可交互原型；并将入口识别、材料完整性、路由正确性、证据可复核性和处理时间纳入验收。

下一步需要用首期目标 Case 验证两个问题：一是研发的标准排查流程能否被 Agent 稳定执行；二是它是否真正缩短从应用工程师接单到问题解决或完成有效转交的时间。在有实测结果前，不宣称准确率或提效比例。
