# AGV 智能诊断产品：STAR 项目讲述底稿

> 这份底稿以产品经理视角讲述。技术实现只用于解释产品取舍，不作为项目主线。标记“待补”的内容不能在正式 interview 中当作确定事实。

## 一句话介绍

公司已有一套面向 AGV 的故障诊断工具，主要提供 Bag 回放、在线连车和行为树分析等专业能力；我主动提出并担任其中 AI Agent 诊断模块的产品经理，面向 Teambition 问题单设计标准化、可追踪、可复用的诊断流程，帮助应用工程师更快判断问题归属模块，并形成带证据的转交材料。

---

## S：Situation，项目背景

公司原有故障诊断工具已经具备 Bag 回放、在线连车和行为树分析等功能，能够帮助工程师查看和分析车辆数据，但它更偏专业分析工具，尚未承接从 Teambition 问题单进入、复用专家经验完成分步诊断和模块归属判断的业务流程。

2026 年 3 月，在公司寻找业务 AI 化机会的背景下，我结合现场项目复盘，发现应用工程师在问题初筛和模块归属判断上存在产品机会，因此提出在既有故障诊断工具中增加 Diagnosis-Agent 模块。我从导航应用工程师处理的 196 个问题单中识别出 36 个错误码类 Bug 和 53 个五类高频问题，合计 89 单，约占 45%。

（访谈部分）我访谈了 4 名应用工程师和 2 名测试人员。
应用工程师帮助我还原现场问题从接单、日志分析到模块转交的实际过程；
测试人员则重点说明 Teambition 单据的提交和流转规则，以及哪些信息必备、哪些 Bag、图片或日志属于可选补充材料。
现场实施工程师遇到问题后，会创建 Teambition 任务，描述问题现象并按需上传材料；
应用工程师接到任务后，再结合问题描述、日志和个人经验判断问题类型及归属模块。

访谈中我发现，错误码类bug和高频问题其实存在相对稳定的排查路径。有经验的应用工程师会按照自己的经验依次检查几个关键环节，但这些步骤主要存在于个人经验中，还没有被整理成统一、可复用的排查计划。

项目二期已经具备日志查询、Topic 检查等基础诊断能力，也由领域研发提供了基于错误码的排查文档。但文档质量和颗粒度参差不齐：部分内容只解释错误码的直接触发条件或处理方式，没有继续梳理上游依赖、对应日志证据和模块归属判断路径，既有能力和知识还没有被组织成 Agent 可执行的完整诊断流程。

因此我判断，当前缺少的不只是更多排查文档或一个自动读取日志的工具，而是一套能够承接问题材料、复用专家经验并持续推进诊断的产品流程：明确第一步检查什么、第二步验证什么、证据不足时如何补充，以及如何把问题收敛到对应模块并形成高质量交接。
产品目标不是替研发解决具体 Bug，而是帮助应用工程师完成其职责范围内的故障诊断和问题分流。

“到点精度异常”是一个典型例子。它在 Q2 导航问题中属于高频提示，但看到这个提示并不能直接判断根因。应用工程师通常需要依次完成五步检查：

1. 确认点位属性和任务场景，是快速到点还是精确到点；
2. 根据三代机型和现场配置，确认实际生效的到点精度阈值；
3. 从同期导航日志中提取实际到点误差，与生效阈值进行比较；
4. 检查到点时间窗口内是否发生定位跳动；
5. 检查控制器结束时误差是否已经收敛。

这五步把一个模糊的“到点不准”现象，逐步收敛到场景或阈值不匹配、实际误差超限、定位不稳定、控制未收敛等可验证方向。

### S 口述版本

公司原有故障诊断工具已经具备 Bag 回放、在线连车和行为树分析等专业能力，但主要解决数据查看和人工分析问题，尚未承接 Teambition 问题单的智能诊断流程。

2026 年 3 月，在公司寻找业务 AI 化机会的背景下，我结合现场项目复盘，发现应用工程师在问题初筛和模块归属判断上高度依赖个人经验，因此主动提出在既有工具中增加 Diagnosis-Agent 模块。

我先分析了导航应用工程师处理的 196 个问题，其中错误码类 Bug 有 36 个，五类高频问题有 53 个，合计 89 个，约占 45%。这说明接近一半的问题具有一定的重复性，值得优先沉淀标准排查能力。

随后，我访谈了 4 名应用工程师和 2 名测试人员，还原了从 Teambition 提单、准备日志和 Bag，到应用工程师分析并转交模块的完整流程。我发现，错误码类 Bug 和高频问题通常存在相对稳定的排查路径，但这些方法主要依赖资深工程师的个人经验，还没有形成统一、可复用的排查计划。

因此，我将产品定位为应用工程师的辅助诊断工具：它不替研发解决具体 Bug，而是承接问题材料，把专家经验转化为可执行、可追踪的诊断流程，帮助应用工程师缩小问题范围、判断归属模块，并形成高质量的转交材料。

## T：Task，我的任务

我虽然正式岗位是软件开发工程师，但在这个项目中担任 AI Agent 诊断模块的产品经理。我不是原有故障诊断工具的整体产品负责人；我的核心任务，是定义 Agent 如何嵌入既有工具，把应用工程师依赖个人经验完成的 Teambition 问题初筛转化为一套可执行、可验证的智能诊断流程，帮助他们更快缩小问题范围并判断归属模块。

围绕这个目标，我主要负责三件事：

1. 规划“错误码诊断＋高频问题诊断”两类核心场景，明确产品边界、诊断流程、人机协同规则及 Agent 调用既有诊断能力的规则；
2. 制定 Agent 可执行的知识标准，协同研发沉淀 150 篇错误码文档和 10 个高频问题排查工作流；
3. 设计产品交互、测试集和验收指标，协调算法与开发完成产品落地，并组织 4 名种子用户进行 50 个真实 Case 的灰度验收。

我的职责重点是场景定义、产品方案、知识标准和效果验收；算法同事负责 Agent 框架与工具执行，领域研发负责错误码知识编写和技术评审，开发同事负责正式系统接入。

## A：Action，我采取的行动

### A1. 收敛首期场景

我没有把产品定义成通用故障诊断，而是聚焦错误码和高频问题两类场景：错误码诊断用于定位直接触发条件和上下游依赖，高频问题诊断用于处理只有现象、没有明确报错的问题。不满足诊断条件的 Case 降级为材料下载和人工排查。首期闭环也不是替研发修复 Bug，而是帮助应用工程师缩小范围、判断归属模块并完成转交。

### A2. 把专家经验转化为 Agent 可执行知识

我定义了统一的知识模板，要求每份知识写清适用版本、触发条件、所需材料、上下游依赖、检查步骤、正常与异常判据以及下一步动作。我协同领域研发根据代码沉淀错误码文档，并与应用工程师共同整理高频问题排查流程。每一步都必须产生可核验的证据；材料不足或证据冲突时，系统只能提示补充材料或转人工，不能强行判断。

针对二期错误码文档质量参差不齐的问题，我设计并向领域研发提供用于错误码知识生成与审核的 Prompt，同时明确输出结构和审核要求。领域研发使用该 Prompt，结合代码仓库定位错误抛出位置、触发条件及相关上游环节，再将这些依赖映射到可检查的日志信息，形成“错误码—直接触发条件—上游原因—日志证据—可能归属模块”的排查链路，并对生成内容进行技术审核。模型输出不直接作为诊断结论，以此降低代码理解偏差和模型幻觉风险。

### A3. 设计并推动产品落地

我将 Agent 作为原有故障诊断工具中的智能诊断模块进行设计：以 Teambition 问题单为核心业务入口，并将内网车辆、远程现场和本地文件作为诊断材料来源。Agent 复用既有工具的数据获取与分析能力，完成材料检查、日志与 Bag 获取、错误码或特征识别、诊断流程匹配和逐项排查，最终展示模块结论、关键证据、已排除方向和下一步建议。

首期错误码诊断复用了二期已有的日志查询、Topic 检查等基础能力。我的产品设计重点不是重新定义或开发这些 Tools，而是明确 Agent 在什么诊断步骤、满足什么条件时调用哪项既有能力，如何将返回结果映射为支持或排除某个方向的证据，再结合审核后的错误码知识推进诊断。

我通过 Vibe Coding 完成前端初版，用可运行原型验证交互，再协调算法同事接入 Agent 和工具能力、开发同事接入正式系统。考虑到现场安全，产品默认只读，高风险操作必须由人工确认。

### A4. 建立测试集并组织灰度

我以应用工程师最终确认的归属模块作为标准答案，建立真实 Case 测试集，并将模块归属收敛率、已收敛 Case 判断准确率和处理时间作为核心指标。离线验证通过后，我组织 4 名种子用户完成 50 个真实 Case 的灰度验收。

针对灰度中出现的材料不足、未匹配诊断流程、过程不可见和证据定位不清等问题，我继续补充失败状态、进度展示、重试、人工接管和证据追溯能力，使产品从“能够执行诊断”进一步走向“过程可控、结果可复核”。

## R：Result，项目结果

项目最终完成了“错误码诊断＋高频问题诊断”两类能力建设，协同研发沉淀 150 篇错误码文档和 10 个高频问题排查工作流，并形成从材料获取、分步排查、证据记录到模块转交的完整产品链路。

在灰度阶段，4 名种子用户使用 50 个真实历史 Case 进行验收。其中 40 个 Case 收敛到唯一模块，模块归属收敛率为 80%；在这 40 个已收敛 Case 中，37 个判断得到应用工程师认可，准确率为 92.5%，简历中概括为约 92%。这里的“闭环”是完成模块归属判断并转交，不是替研发修复具体 Bug。

效率方面，典型软件 Bug 的初筛和模块转交时间由约 60 分钟缩短到约 10 分钟。按照灰度样本的节省时间和 4 名种子用户的季度问题量外推，2026 年 Q2 预计可减少约 95 小时的问题排查时间；这个数字是测算值，不是系统埋点统计的实际累计值。

灰度后，我进一步明确了产品边界：只有高频问题、有错误码或有明确特征的 Case 才进入智能诊断；其他问题降级为材料下载，由应用工程师继续人工排查。灰度期间未触发高风险操作，所有 Case 的最终判断均以应用工程师复核结果为准。

## 2 分钟口述底稿

这是一个面向 AGV 应用工程师的技术支持诊断 Agent。我负责在公司既有故障诊断工具中规划 AI 诊断模块，把原本依赖个人经验的问题初筛，转化为标准化、可执行、可追溯的诊断流程。

项目初期，我通过历史问题复盘，分析了上季度的 196 个导航相关问题，其中错误码类 Bug 和五类高频问题共 89 个，占比约 45%。随后我访谈了应用工程师和现场人员，还原了从 Teambition 提单、准备日志和 Bag，到问题分析和模块转交的完整流程，发现其中大量前置排查动作具有重复性，并且存在相对稳定的诊断路径。

产品方案上，我将首期范围收敛为“错误码诊断＋高频问题诊断”两条路径。Agent 负责理解问题、选择诊断路径并推进流程，具体排查动作则沉淀为基于日志和 ROS Bag 的标准 Workflow，并复用原有故障诊断工具的数据能力获取证据。

针对历史错误码文档质量不统一的问题，我向领域研发提供知识生成 Prompt、输出结构和审核要求，要求补全错误抛出位置、上游原因、日志证据和模块归属链路，最终推动沉淀 150 篇错误码文档和 10 个高频问题排查工作流。

对于知识未覆盖、材料不足或证据冲突的 Case，系统不会强行给出结论，而是提示补充材料或转人工复核。

灰度阶段，我们用 50 个真实 Case 进行验证，其中 40 个收敛到唯一模块，模块归属收敛率为 80%；已收敛 Case 中有 37 个判断正确，准确率约 92%。典型软件 Bug 的初筛和模块转交时间由约 60 分钟缩短到 10 分钟。

这个项目的核心不是让 Agent 自主解决 Bug，而是把专家经验转化成有证据、可复核、可交接的诊断流程。

**AGV 技术支持诊断 Agent｜模块产品经理（正式岗位：软件开发工程师）**
