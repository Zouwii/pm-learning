# Diagnosis-Agent

## 一句话

面向 AGV 技术支持的诊断 Agent：根据问题描述选择唯一数据入口，自动采集日志与任务材料，组合规则、错误码、文档和历史 Case 形成证据链，输出诊断报告与人工交接材料。

## 这个项目证明什么

- 从高频人工流程中识别适合 Agent 的任务；
- 划清 Agent、确定性 Engine 和领域工具的职责；
- 设计条件路由、证据融合、降级和 Human-in-the-Loop；
- 用证据和结论状态约束模型，而不是让模型直接猜根因；
- 规划从发现异常到理解异常、协助解决异常的演进。

## 用户问题

技术支持排查问题时需要手动 SSH、找日志、grep、查错误码、搜索内部文档和代码。流程耗时且依赖老工程师经验，Case 结束后知识也难以沉淀。

## 架构边界

| 层 | 职责 |
| --- | --- |
| Agent / LangGraph | 理解输入、规划路径、融合证据、决定追问或转人工 |
| 确定性 Engine | SSH/TB 采集、日志裁剪、正则扫描和 Case 落盘 |
| Playbook / 知识层 | 错误码、SOP、历史 Case 和模块关联 |
| FastAPI + SSE | Case API、状态查询、进度推送和报告下载 |

一次 Case 只选择 TB、内网机器人、远程现场或本地日志中的一个采集入口，避免上下文混乱和重复采集。

## 当前真实状态

正式讲述必须说“正在开发/验证”，不能说成已全量上线。

## 30 秒讲法

我正在做一个面向 AGV 技术支持的 Diagnosis-Agent。它不是让 LLM 直接读日志猜答案，而是由 Agent 识别问题和规划路径，确定性引擎负责 SSH、日志裁剪和规则扫描，再从错误码、知识库、代码和历史 Case 中补充证据。系统根据证据充分度输出 confirmed、likely、need_human 或 insufficient_data，从架构上控制幻觉和误操作风险。
