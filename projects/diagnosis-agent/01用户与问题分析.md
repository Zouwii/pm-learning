# Diagnosis-Agent 用户、场景与产品职责

## 1. 产品背景

AGV 现场问题的材料分散在 Teambition 任务、机器人环境、远程现场和本地日志包中。技术支持需要在多个系统之间切换，手动收集材料、搜索日志、查询错误码和历史经验，再将复杂问题转交研发。

公司的算法同事已经提供 `diagnosis-orchestrator`、标准化 Skill 规范以及部分场景 Skill。项目并不是从零训练一个诊断模型，而是将已有算法能力接入产品，并补齐缺失场景、交互、流程和安全边界。

## 2. 用户角色

### 一线技术支持

- 目标：快速收集有效材料，判断问题方向，完成初步排查或高质量转交。
- 痛点：入口分散、步骤重复、依赖经验、材料经常不完整。

### 研发和领域专家

- 目标：基于完整上下文和证据定位复杂根因。
- 痛点：收到的问题缺少时间、版本、日志窗口和已执行步骤，需要重复补问。

### 产品与系统管理员

- 目标：控制工具权限，了解执行状态，沉淀可复用 Case。
- 痛点：纯终端对话不方便统计、审计、恢复和评估。

## 3. 四类诊断场景

一次 Case 只选择一个主要来源，避免重复采集和上下文混乱。

| 场景 | 用户输入 | 系统主要动作 | 主要风险 |
| --- | --- | --- | --- |
| Teambition 任务 | 任务链接或任务标识 | 读取任务、活动记录和附件，整理问题上下文 | 授权失败、附件缺失、任务描述不完整 |
| 公司内网机器人 | 机器人连接信息和问题现象 | 在授权范围内只读采集状态与日志 | 误操作现场设备、采集范围过大 |
| 客户远程现场 | 远程现场信息和问题现象 | 获取远程材料并整理交接信息 | 网络和权限不可控、现场操作风险 |
| 本地日志包 | 用户上传的日志与问题描述 | 解压、扫描、截取时间窗并执行规则分析 | 路径越界、日志时间不明确、材料不完整 |

在需求梳理时，算法侧已有其中两个场景的 Skill。ZHR 指出完整业务链路还需要 Teambition 类型的 Skill，用于读取任务信息、活动记录和附件。已有两个 Skill 的准确名称需要在面试前用需求记录或仓库证据确认，不临时推测。

## 4. ZHR 的产品职责

### 场景和工具需求

- 将诊断需求抽象成四类固定入口；
- 明确每类入口需要的输入、工具、输出和异常处理；
- 识别 Teambition Skill 缺口，并提出对应能力需求；
- 约束一个 Case 只选择一个主要来源。

### 交互设计

- 设计场景选择、参数输入、AI 诊断会话和结果查看流程；
- 定义材料不足、权限失败和需要人工介入时的反馈；
- 将产品方案交由开发同事完成平台接入和工程实现。

### 路线与边界

- 决定先用 Claude + Skill + ttyd 验证诊断价值；
- 根据 MVP 暴露的问题，定义 LangGraph 产品化升级范围；
- 明确默认只读、高风险操作人工确认、Case 隔离和工具审计要求；
- 定义真实 Case 对比与后续验收方法。

## 5. 团队分工口径

| 角色 | 主要贡献 |
| --- | --- |
| ZHR / 产品经理 | 场景抽象、Skill 缺口识别、交互设计、MVP 路线、产品化范围、安全边界和验收设计 |
| 算法同事 | 提供 orchestrator、Skill 规范和领域诊断能力，开发或补充对应 Skill |
| 开发同事 | 评估并实现平台技术方案；MVP 使用 ttyd 承载 Claude Code/Skill 运行环境，后续建设 Case API、工作流和前端能力 |

讲述时不能把团队已有的 orchestrator、Skills 或开发实现包装成个人开发成果。ZHR 的价值是定义正确的问题、补齐能力缺口，并推动算法能力成为可使用、可控制的产品。

## 6. 核心产品判断

第一阶段最重要的未知量是“已有诊断知识和 Skills 能否帮助技术支持解决真实问题”，而不是“能否搭建 LangGraph”。因此 MVP 优先复用 Claude 已有的 Agent Loop 和工具调用能力，通过 ttyd 快速接入平台。

在能力得到初步验证后，再解决 Case 管理、过程追踪、失败恢复、安全控制和节点级评估问题。这构成从 Claude MVP 演进到 LangGraph 的产品逻辑。

- ttyd MVP 的真实使用 Case；
- origin-v1 与 origin-split 的一致性验证结果。
