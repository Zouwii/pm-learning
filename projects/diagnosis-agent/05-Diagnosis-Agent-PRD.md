# AGV 技术支持诊断 Agent 产品需求文档

## 1. 项目概述

### 1.1 项目背景

AGV 现场问题持续增长，单个问题可能涉及导航、定位、调度、感知、本体或现场配置等多个模块。应用工程师收到 Teambition 问题单后，需要理解现象、核对材料、查询错误码、分析日志与 ROS Bag，再判断问题归属或转交研发。

当前排查方式存在三个主要问题：

1. **依赖个人经验**：不同经验水平的工程师排查顺序和结论质量不一致；
2. **重复劳动较多**：高频问题和错误码问题反复执行相似的材料检查与日志分析；
3. **交接信息不完整**：问题现象、已执行步骤和判断证据没有统一结构，研发仍需重复补问。

历史问题复盘显示，196 个导航相关问题中有 36 个错误码类 Bug 和 53 个高频问题，合计 89 个，约占 45%。这两类问题具有较明确的识别特征和相对稳定的排查路径，适合作为首期产品范围。

### 1.2 产品定位

面向 AGV 应用工程师的辅助诊断 Agent，将错误码知识和高频故障排查经验转化为标准化、可执行、可追踪的诊断能力，帮助用户完成：

问题理解 → 路径选择 → 分步排查 → 证据汇总 → 模块收敛或人工交接。

产品不替代领域研发解决具体 Bug，也不将模型输出直接作为最终责任判定。

### 1.3 产品目标

- 建立“错误码诊断＋高频故障诊断”双路径；
- 统一诊断知识与 Workflow 的结构和审核标准；
- 自动完成重复性的材料读取、特征提取和标准检查；
- 输出可复核的模块归属建议、关键证据和已排除方向；
- 对材料不足、证据冲突和能力未覆盖的问题明确转人工；
- 通过真实 Case 验证问题收敛效果、结果准确性和处理效率。

## 2. 用户与使用场景

### 2.1 目标用户

| 用户 | 核心诉求 |
| --- | --- |
| 应用工程师 | 快速理解问题、完成初筛并判断责任模块 |
| 现场实施与测试人员 | 明确需要提交的材料，减少反复沟通 |
| 模块研发 | 获得包含现象、证据和已排除方向的标准交接材料 |
| 产品及管理员 | 查看使用效果、Bad Case 与知识覆盖情况 |

### 2.2 首期场景

#### 场景一：错误码诊断

问题材料中存在明确错误码。系统结合错误码知识、软件版本、日志和上下游状态，检查直接触发条件及潜在根因，避免将抛错模块直接判定为责任模块。

#### 场景二：高频故障诊断

问题没有可直接定位的错误码，但属于已经沉淀的高频故障场景。系统匹配对应 Workflow，按照标准步骤逐项检查，逐步缩小问题范围。

### 2.3 非目标

- 不处理所有长尾和未知故障；
- 不替代研发进行代码修改、现场复现和最终 Bug 修复；
- 不在证据不足时强制输出唯一责任模块；
- 不自动执行重启、参数修改、软件升级等高风险操作；
- 不把“完成模块转交”表述为“完成 Bug 修复”。

## 3. 核心产品方案

### 3.1 Workflow 与 Agent 协同

| 角色 | 职责 |
| --- | --- |
| Agent | 理解问题、提取错误码与现象、选择诊断路径、组织证据和解释结果 |
| Workflow | 按标准步骤调用日志、ROS Bag、配置等既有诊断能力，并依据条件推进分支 |
| 应用工程师 | 补充材料、复核诊断结果、决定继续排查或转交研发 |

设计原则：

- Agent 处理非结构化输入与路径决策；
- Workflow 保证关键检查不被遗漏，并使过程可复现；
- 每个判断必须关联事实证据；
- 人工拥有最终复核权并承担高风险操作。

### 3.2 端到端流程

1. 用户提交 Teambition 问题单并创建诊断 Case；
2. 系统读取问题描述、活动记录和附件；
3. 检查问题时间、软件版本及关键诊断材料是否完整；
4. Agent 提取错误码、问题现象和任务阶段；
5. 系统选择错误码诊断或高频故障 Workflow；
6. Workflow 调用既有能力执行日志、Bag 和配置检查；
7. 系统保存每个步骤的状态、判断与原始证据；
8. 能够收敛时输出唯一责任模块及证据；
9. 无法收敛时输出候选方向、已排除项、缺失材料及人工建议；
10. 应用工程师复核结果并完成交接或继续人工排查。

### 3.3 结论状态

| 状态 | 定义 |
| --- | --- |
| 已收敛 | 完成关键检查，输出唯一责任模块，并具有相应证据 |
| 范围缩小 | 已排除部分模块，但仍存在两个及以上候选方向 |
| 待补材料 | 缺少继续诊断所必需的时间、版本、日志、Bag 或配置 |
| 转人工 | 已完成产品能力范围内的检查，仍需现场操作或领域专家判断 |
| 执行失败 | 因权限、网络、工具或文件异常未完成流程 |

## 4. 功能需求

### FR-01：创建诊断 Case

系统读取 Teambition 问题单，创建唯一 Case，并保存问题描述、发生时间、版本信息、附件清单和发起人。

验收标准：

- 能够通过有效问题单创建唯一 Case；
- 自动提取的信息向用户展示并允许补充；
- 关键信息缺失时明确提示缺失项；
- 同一 Case 的输入、过程和结果能够持续保存。

### FR-02：检查材料完整性

系统在执行诊断前检查问题时间、软件版本及目标流程需要的日志、ROS Bag 或配置。缺失材料时暂停诊断并提示补充，不进入无证据推理。

验收标准：

- 能够根据目标场景展示必需材料清单；
- 能够区分已获取、缺失、读取失败和需要授权；
- 补充材料后可以继续原 Case；
- 材料不足不得输出确定性模块结论。

### FR-03：识别并路由诊断场景

Agent 从问题描述和材料中提取错误码、问题现象和任务阶段，并路由至错误码诊断或已配置的高频故障 Workflow。

验收标准：

- 明确错误码能够匹配相应知识；
- 高频现象能够匹配相应 Workflow；
- 多个候选路径时展示匹配依据并允许人工确认；
- 无匹配路径时直接进入人工排查，不由模型自由生成诊断步骤。

### FR-04：执行错误码诊断

系统根据错误码知识检查适用版本、直接触发条件、上游依赖、日志证据与可能归属模块。

验收标准：

- 展示错误码含义、适用版本和检查路径；
- 能够调用对应工具完成必要检查；
- 区分报错模块与潜在根因模块；
- 关键证据不足时不得直接收敛；
- 结论能够追溯到具体日志、配置或代码知识。

### FR-05：执行高频故障 Workflow

系统按照预设的检查顺序和条件分支执行高频故障排查。每一步包含检查对象、所需工具、判断标准、证据及下一步动作。

验收标准：

- 能够按顺序及条件分支执行检查；
- 页面展示当前步骤、已完成步骤与执行结果；
- 条件不满足时进入正确分支或停止；
- 中断后能够保留已有步骤和证据；
- 未达到收敛标准时输出候选方向而非唯一结论。

### FR-06：展示进度与异常

系统展示材料读取、场景识别、流程执行、报告生成和等待人工等状态。发生异常时说明失败步骤、原因和可执行动作。

验收标准：

- 用户能够查看当前步骤及整体进度；
- 权限、网络、工具和材料异常能够区分；
- 支持安全重试或补充材料后继续；
- 无法恢复时保留现有证据并转人工。

### FR-07：记录与引用证据

系统将事实证据与 Agent 判断分开保存，标记证据来源、时间窗、对应步骤及支持或排除的方向。

验收标准：

- 每个关键判断至少关联一项可核验证据；
- 用户能够定位到原始日志、Bag、配置或知识条目；
- 相关性证据不能直接标记为因果结论；
- 证据冲突时展示冲突，不强制选择唯一方向。

### FR-08：生成报告并人工复核

诊断报告包含问题摘要、命中场景、执行步骤、模块建议、关键证据、已排除方向、缺失材料和下一步建议。

应用工程师可以选择认可、补充材料或转人工，并记录实际判断。

验收标准：

- 报告结构完整且证据可追溯；
- 未收敛时明确展示原因和下一步；
- 未经复核的结果不得标记为最终结论；
- 复核反馈能够保存并用于 Bad Case 分析。

### FR-09：管理诊断知识与 Workflow

错误码知识和高频 Workflow 需要记录适用版本、维护人、审核状态和更新时间。新增或修改后需经过领域研发审核再发布。

验收标准：

- 未审核内容不能进入正式诊断；
- 能够按错误码、场景和版本检索；
- 历史 Case 保留当时使用的知识版本；
- 过期或不匹配版本的知识不能直接用于确定性结论。

## 5. 知识建设规范

### 5.1 错误码文档

每篇文档应包含：

- 错误码、现象、适用机型和软件版本；
- 代码抛错位置与直接触发条件；
- 上游依赖、可能原因与责任模块；
- 所需日志、配置或 Bag 证据；
- 检查步骤、判断标准、下一步动作；
- 维护人、审核人和更新时间。

### 5.2 高频诊断流程

每套流程应包含：

- 适用与排除条件；
- 所需材料；
- 步骤顺序与条件分支；
- 每步调用能力、输入及预期输出；
- 正常与异常判据；
- 收敛、停止及人工接管条件。

### 5.3 内容生产机制

- 产品经理定义结构、适用规则和验收要求；
- 模型可辅助从代码与文档中生成初稿；
- 领域研发确认技术事实和上下游关系；
- 应用工程师验证流程是否符合真实排查习惯；
- 正式发布后根据 Bad Case 持续迭代。

首期沉淀范围为 150 篇错误码排查文档和 10 套高频诊断流程。

## 6. 测试与验收

### 6.1 测试集口径

| 项目 | 定义 |
| --- | --- |
| 测试集 | 从首期可覆盖场景中筛选的 50 个真实历史 Case |
| 输入 | 原始问题描述、时间、版本及当时可获得的诊断材料 |
| 标准答案 | 应用工程师复核确认的最终归属模块 |
| 特殊样本 | 材料不足或无法唯一归属时保留真实状态，不强设答案 |
| 版本控制 | 固定 Agent、Workflow、诊断知识与工具版本 |

该测试集为目标场景专项评测集，不是从全部问题中随机抽样，因此结果不能代表所有 AGV 故障。

### 6.2 核心指标

| 指标 | 计算方式 | 当前结果 |
| --- | --- | ---: |
| 模块归属收敛率 | 输出唯一模块且有证据支持的 Case 数 ÷ 全部测试 Case 数 | 40/50 = 80% |
| 已收敛 Case 判断准确率 | 人工复核正确数 ÷ 已收敛 Case 数 | 37/40 = 92.5% |
| 全量正确定位率 | 正确收敛至唯一模块的 Case 数 ÷ 全部测试 Case 数 | 37/50 = 74% |
| 高风险操作次数 | 未经确认执行高风险操作的次数 | 0 |

效率指标需要说明统计边界：

- 典型软件故障的初筛和模块转交时间由约 60 分钟缩短至约 10 分钟，降低 80%+；
- 季度节省约 95 小时为基于灰度样本和种子用户问题量的外推测算，不是埋点累计数据。

详细评测口径见 [04-测试集数据说明.md](04-测试集数据说明.md)。

### 6.3 Bad Case 分类

| 分类 | 典型原因 | 优化方向 |
| --- | --- | --- |
| 材料不足 | 时间、版本、日志或 Bag 缺失 | 增加完整性校验和补充提示 |
| 未匹配 Workflow | 场景未覆盖或表达歧义 | 补充高价值流程或转人工 |
| SOP 粒度不足 | 只能缩小范围，无法定位单一模块 | 细化检查项和判断标准 |
| 跨模块证据耦合 | 多个模块同时出现关联异常 | 增加上下游因果检查 |
| 相关性误判 | 将同时出现的异常当作根因 | 提高收敛门槛并要求正向证据 |
| 执行异常 | 权限、网络、工具或文件失败 | 增加状态、重试和人工接管 |

## 7. 数据、安全与权限

- 诊断 Case 按用户和项目权限隔离；
- 凭据不写入模型上下文、日志或报告；
- 工具和参数使用服务端白名单；
- 诊断过程默认只读；
- 高风险操作必须由有权限的用户二次确认；
- 报告保留知识版本、工具调用摘要和复核记录；
- 敏感附件和日志遵循公司存储与保留规则。

## 8. 团队分工

| 角色 | 主要职责 |
| --- | --- |
| 产品经理 | 用户研究、MVP 范围、双路径方案、知识标准、交互、安全边界、指标和验收 |
| 算法/AI 研发 | Agent 框架、场景识别、工具编排和结果生成 |
| 平台开发 | Case 管理、页面交互、权限、状态与系统集成 |
| 领域研发 | 错误码知识编写、技术审核和复杂 Case 复核 |
| 应用工程师 | 高频流程共创、真实 Case 验证和结果反馈 |

## 9. 迭代计划

### 阶段一：需求与知识准备

- 复盘历史问题并访谈目标用户；
- 收敛错误码与高频故障两类场景；
- 制定错误码文档和 Workflow 标准；
- 完成首批知识与流程审核。

### 阶段二：MVP 与离线评测

- 跑通问题单读取、场景路由、流程执行、证据记录和报告复核；
- 使用真实历史 Case 进行离线验证；
- 根据未收敛、误判和执行失败调整知识与流程。

### 阶段三：灰度与上线试运行

- 面向种子应用工程师开放；
- 记录收敛率、准确率、处理时长及人工接管原因；
- 补充进度展示、失败重试和证据追溯；
- 仅在知识与流程审核通过后扩大覆盖范围。

## 10. 个人职责边界

产品经理负责发现问题、界定场景、设计方案和验收，不将算法框架、工具开发或领域知识编写全部表述为个人开发成果。

本项目中的个人主责口径为：

- 复盘历史问题并访谈应用工程师，确定 MVP 范围；
- 规划错误码诊断与高频故障诊断双路径；
- 设计 Workflow 与 Agent 协同机制、诊断边界及人工接管策略；
- 制定错误码知识和高频流程的结构化标准；
- 协调业务、领域研发、算法和平台开发完成产品落地；
- 构建 50 Case 测试集与验收指标，根据 Bad Case 推动迭代。
